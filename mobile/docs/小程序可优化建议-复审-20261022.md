## 一、我的判断（先说结论）

**三句话：**

1. **上午那份清单的判断没错，但只落地了分包一项。** 其余 8 项（隐私、请求封装、分页、更新提示、错误上报、tabBar 权限、图片链路、detail 拆分）**零进展**。其中**隐私合规是唯一"不做就 100% 驳回"的硬门槛**，其他都只是体验债。
2. **分包之后，新瓶颈已经不在包体，而在请求层。** 213 处裸 `uni.request`、3 套 header 写法、67 处 `code === 0` 与 34 处 `statusCode` 两套返回码判断、失败后一律渲染"暂无记录"。这是"用户骂"的主要来源，不是包体。
3. **必须说清楚一件事**：小程序端做再多"401 清 token 跳登录"都是空转 —— 后端根本不校验 token，永远不会返回 401。**前端优化解决体验，不解决安全。** 安全在 `docs/鉴权加固方案-v2.5.0.md`（326 路由 134 个零校验、密码明文），那是另一个版本的事，别指望这轮前端改动顺手带上。

**优先级排序（这版真正值得做的 5 件）**：隐私合规 → 空/错态区分 → 分页 bug → 图片二次压缩 → 更新提示 + 错误上报。前 3 件加起来约 1.5 天，能把"用户觉得这 App 坏了"的比例压下去一大半。

## 二、清单外的新发现（8 条，这次才测出来的）

### 1. 首页一个页面拉 4 次 `/api/projects`

| 位置 | 用途 |
|---|---|
| `pages/home/index.vue:374` | 首页正常加载项目 |
| `:462` | `openProjectPicker`（通用项目选择弹窗） |
| `:509` | `openMaterialPicker`（主材操作选择） |
| `:555` | `openGanttPicker`（甘特图项目选择） |

后三份代码**几乎逐行相同**（`showLoading` → 全量拉 `/api/projects` → 弹 `bottom-picker`），只是回调不同。

而 `utils/projectPicker.ts` 里**已经有** `pickProject()` 这个共享实现，全项目只有 `pkg-inspect/dispatch/list.vue:132` 一个调用点 —— 也就是说**共享轮子造好了但没人用**。

- 影响：首页 8 个请求里 4 个打同一个接口；项目数上到 300 时，每开一次选择器就拉 300 条大对象。
- 建议：三处改用 `pickProject()`，并在 `projectPicker.ts` 里加 5 分钟内存缓存 + 并发去重（同时点两次只发一次请求）。
- 改动量：约 1 小时，删掉 200+ 行重复代码。

### 2. 75 处 `Authorization: token` 是无效头，而且三套 header 写法并存

| 写法 | 数量 | 实际效果 |
|---|---|---|
| `header: { Authorization: token }` | **75 处** | 后端从不校验 Authorization，纯装饰 |
| `header: authHeader()` | 3 处 | 与上者语义重叠 |
| 完全不传（靠 `App.vue` 全局拦截器注入 `x-user-id` / `x-user-role` / `x-user-type`） | 其余 135 处 | 唯一真正生效的路径 |

而且 `token` 的值是 `'logged_in'` 这类兜底字符串（PC 端同样问题），不是真令牌。

- 风险：无功能收益，但**后天上 token 校验时这 75 处会一起挂**（值不对）。
- 建议：二选一，不要再三种并存 —— 要么统一改 `Authorization: Bearer <token>`（为 v2.5.0 铺路），要么删干净统一走拦截器。**跟统一请求封装一起做，别单独排一次回归。**

### 3. 分页是"半实现"，而且有一个跳页 bug

事实修正：上一份清单写"0 处分页"已经不准确了 —— 现在 **12 个页面有 `loadMore`**、11 个有 `pageSize`、9 个用 `@scrolltolower`。但它们全走 `<scroll-view @scrolltolower>`，`onReachBottom` / `onPullDownRefresh` 仍然是 **0**（意味着没有下拉刷新，且页面级滚动不会触发加载）。

**真 bug** 在 `pkg-finance/finance/list.vue:122-125`：

```js
function loadMore() {
  if (loadingMore.value || noMore.value) return
  loadingMore.value = true
  page.value++          // ← 先推进页码，再发请求
  uni.request({ ... data: { page: page.value, page_size: pageSize } ... })
}
```

请求失败时页码已经推进，下次成功会**整页跳过**（第 2 页的数据永久看不到）。同类写法在其它 11 页大概率一致，需要逐个核。

另外 `records.value = [...records.value, ...list]` 每页都重建整个数组，20 页时 setData 要传 400 条大对象。

- 建议：抽一个 `usePagedList(fetcher)` composable —— 页码只在 `success` 里推进、用 `push` 追加、`noMore` 由"返回条数 < pageSize"和"页码上限"双条件判定、失败保持当前页可重试。
- 改动量：composable 半天，替换 12 页再半天。

### 4. 74 个页面手写 `class="nav-bar"`，`top-nav.vue` 是死代码

- `grep -rl 'class="nav-bar"'` = **74 个文件**（正好每个页面一份）
- `pages.json` **没有 easycom 配置**（实测 `easycom` 键不存在）
- 每页还要各自写 `:style="navStyle"` 做状态栏安全区

- 影响：改一个返回按钮的点击热区要改 74 处，必然漏；这也是"两端同步"成本高的根源之一。
- 建议：配 easycom（`"^nav-bar$": "@/components/nav-bar.vue"`），抽 `<nav-bar title :show-back>` + slot；**逐页替换，先从新写的页面开始**，老页面不动。不要一次性改 74 页（回归成本远超收益）。
- 定性：这是**架构债不是 bug**，别放进这版。

### 5. "空"和"错"没区分 —— 这条最伤用户信任

- 213 处请求里 **101 处有 `fail:`**，但 fail 里多是 `console.log` / 一句 `showToast`，列表数据保持 `[]` → 页面照常渲染"暂无记录"。
- 典型：`projects/list.vue` 的 `catch` 里直接 `return { data: [] }`。

- 影响：**服务器挂了 / 断网时，用户看到的是"我的项目没了"**。比弹一个报错吓人得多，而且直接打电话给你。
- 建议：任何列表页做三态 —— `loading`（骨架）/ `empty`（真没数据）/ `error`（"网络异常，点击重试"按钮）。这条必须落在统一请求封装里，否则又是一次 74 页手工回归。

### 6. 数据加载时机：61 个文件用 `onMounted`，只有 9 个用 `onShow`

| 生命周期 | 命中文件数 |
|---|---|
| `onMounted` | **61** |
| `onLoad` | 11 |
| `onShow` | 9 |
| `onUnload` | 1 |

小程序里 **tabBar 页和 `navigateBack` 回来的页面实例是复用的**，`onMounted` 只跑一次。

- 影响：切回"项目""巡检"tab 看到的是上次的旧数据；在详情页审批完返回列表，状态不变，用户以为没成功。
- 建议：列表/详情页统一在 `onShow` 拉数据（或 `onShow` 里判断 `needRefresh` 才拉），`onMounted` 只做初始化。**首页 `pages/home/index.vue` 的 8 个请求尤其要挪**，否则待办数量永远不更新。

### 7. `compressImage` 全项目只有 1 个页面用了

- 只有 `pkg-misc/mine/my-logs.vue:199` 自己写了一份压缩逻辑。
- 其余上传统一走 `utils/api.ts` 的 `chooseAndUpload()`，`sizeType: ['compressed']` 之后**没有二次压缩**，单张仍常 1~2 MB。

- 建议：把 `my-logs.vue` 那 20 行搬进 `chooseAndUpload()`（长边 1600 / quality 70），**改一处全站生效**。
- 改动量：**30 分钟**，这是本轮性价比最高的单项。
- 附带：`<image>` 目前 **0 处 `lazy-load`**。工地相册页 20 张原图 = 可能 40 MB 流量，加个 `lazy-load` + 固定宽高（防布局抖动）成本极低。

### 8. 3 个孤儿页还在磁盘上

`pages/index/index.vue`、`pages/mine/mine.vue`、`pages/projects/projects.vue` —— `pages.json` 未声明、无任何引用、不参与构建。

- 影响：只是仓库噪音，但**会误导后来的人和 AI**（我这次复审就先点进了 `pages/mine/mine.vue` 才发现是空的）。
- 建议：确认后删除，或在 `docs/` 里标一句"已废弃"。

### 顺带核实（这两条是**好消息**，别误改）

- `lazyCodeLoading: requiredComponents` **在构建产物 `dist/build/mp-weixin/app.json` 里是生效的**，不是只在 `manifest.json` 里写了好看。
- 分包结构落地正确：主包 **18 页** + 5 个分包 **57 页** = 75 页，`preloadRule` 4 条全部指向真实存在的页面。

## 四、这版**不要**做（避免过度工程）

- ❌ **不引 UI 框架**（uView / TDesign）：包体回涨 300~500 KB，把分包省下的空间吃回去。
- ❌ **不上 TS 强类型全覆盖**：2 周工作量，审核和运维都不看这个。
- ❌ **不同步 H5 分包**：H5 没有 2 MB 上限，且在线上跑着，改目录=改路由，风险不对称。
- ❌ **不为了"统一"抹平台差异**：`navStyle` / `absAsset` / `statusSlug` 这些是平台必需项。
- ❌ **不要在小程序端写完整的 401 跳登录逻辑**：后端没 401，写了就是死代码。等 v2.5.0 鉴权加固一起上。
- ❌ **不要单独排一次"改 75 处 Authorization"**：跟请求封装合并，避免两次全站回归。

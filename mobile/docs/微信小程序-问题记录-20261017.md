### 3️⃣ WXSS 编译错误：选择器含中文

**现象**：
```
[WXSS 文件编译错误] ./pages/customer/project-detail.wxss(1:8559): unexpected \ at pos 8559
```

**根因**：CSS 选择器里写了中文，例如 `.status-待整改`。
构建时中文被转义成 Unicode 转义序列 → `.status-\5f85\6574\6539`，
而 **微信 WXSS 不认反斜杠转义**，直接编译失败。

**处理**：中文状态映射为 ASCII 类名。

```js
// my-inspections.vue
const statusSlug = (status) => {
  const map = { '待处理': 'pending', '处理中': 'processing', '已完成': 'done' };
  return map[status] || 'pending';
};
// 模板
:class="`status-${statusSlug(item.status)}`"
```

涉及 3 个文件：
- `pages/customer/project-detail.vue` —— 死代码中文选择器（模板零引用）→ 直接删除
- `pages/mine/my-inspections.vue` —— 活代码 → 加 `statusSlug()`
- `pages/projects/detail.vue` —— 活代码 → 加 `statusSlug()`（4 种状态：pending/fixing/review/done）

**全量校验**：77 个 wxss 产物反斜杠数 = 0；源码 81 个 `<style>` 块全 ASCII。

> 📌 **教训**：第一轮只扫了「反斜杠」这一类，没顺带扫 `*`，导致又来回一轮。
> **正确做法是一次把所有已知的 WXSS 差异扫全。**

### 5️⃣ 请求地址全是相对路径（223 处）

**现象**：小程序里所有接口都请求不到。

**根因**：项目原本写 `uni.request({ url: '/api/xxx' })`。
H5 端同源没问题，但**小程序 `uni.request` 不接受相对路径**，必须绝对 HTTPS URL。
构建产物里 `/api/` 出现 **223 次**，绝对域名 **0 次**。

**处理**：新增统一出口 `src/utils/api.ts`，按平台条件编译：

```ts
let origin = '';
// #ifdef MP-WEIXIN
origin = 'https://erp.fujinwanjia.com';
// #endif
// #ifdef APP-PLUS
origin = 'https://erp.fujinwanjia.com';
// #endif
// #ifdef MP-ALIPAY
origin = 'https://erp.fujinwanjia.com';
// #endif
export const API_ORIGIN = origin;

export function absUrl(url: string): string { /* 补前缀，H5 原样返回 */ }
export function absAsset(path: string): string { /* 静态资源补全 */ }
```

然后在 `App.vue` 里拦截 4 个 uni API，统一补全：

```js
const _origRequest = uni.request.bind(uni);
uni.request = (options) => {
  options.header = buildHeaders(options, true);
  options.url = absUrl(options.url);
  return _origRequest(options);
};
// 同理：uni.uploadFile / uni.downloadFile / uni.previewImage
```

**为什么走拦截器而不是逐个改 223 处**：改动点集中在一个文件，且新增页面自动生效。

### 6️⃣ 登录失败 —— 最隐蔽的一个 ⭐

**现象**：小程序能打开，但用**正确的**账号密码登录，后端返回「用户名或密码错误」。

**排查过程**（走了弯路，记录如下）：

| 阶段 | 判断 | 结果 |
|---|---|---|
| 1 | 怀疑密码不对，从服务器 DB 直接查出真实账号 `admin/admin123` | 让用户重试 → 仍失败 ❌ |
| 2 | 做**对照实验**：同一接口、同一正确凭据，只改一个变量 | 见下表 → 定位成功 ✅ |

**决定性对照实验**：

| 请求头 | 结果 |
|---|---|
| `Content-Type: application/json` | ✅ 登录成功 |
| `Content-Type: application/x-www-form-urlencoded` | ✅ 登录成功 |
| **不带正确 Content-Type** | ❌ 返回 54 字节「用户名或密码错误」 |

**真根因**：

```
uni 运行时在小程序端不补默认 Content-Type
  → express bodyParser.json() 拿不到 body
  → req.body 变成空对象 {}
  → SQL 用空条件匹配不到任何行
  → 后端返回「用户名或密码错误」（误导性的错误信息）
```

**为什么以前没暴露**：H5 端 XHR 会自动带上 `application/json`，所以这个 bug **只在移植到小程序时出现**。

**佐证**：源码里已有 15 处手写 `Content-Type: application/json`，**全是 POST** ——
说明这个坑被反复踩过、每次手写绕过，唯独登录页漏了。

**处理**：`App.vue` 新增 `buildHeaders()` 全局兜底。

```js
const hasContentType = (headers) =>
  Object.keys(headers).some((k) => k.toLowerCase() === 'content-type');

const buildHeaders = (options, allowJsonDefault) => {
  const headers = options.header || {};
  // 1) 注入身份头
  const userInfo = uni.getStorageSync('userInfo');
  if (userInfo?.id) headers['x-user-id'] = userInfo.id;
  if (userInfo?.role_code || userInfo?.role_name) {
    headers['x-user-role'] = userInfo.role_code || userInfo.role_name || '';
  }
  // 2) 兜底 Content-Type（调用方已显式指定的绝不覆盖）
  const method = String(options.method || 'GET').toUpperCase();
  const d = options.data;
  const isBinary = typeof ArrayBuffer !== 'undefined' && d instanceof ArrayBuffer;
  if (
    allowJsonDefault && !hasContentType(headers) &&
    method !== 'GET' && method !== 'HEAD' &&
    d !== undefined && d !== null && typeof d === 'object' && !isBinary
  ) {
    headers['Content-Type'] = 'application/json';
  }
  return headers;
};
```

> ⚠️ **关键细节**：`uni.uploadFile` 必须传 `allowJsonDefault = false`。
> **绝不能给 uploadFile 补 `application/json`** —— multipart 的 `Content-Type`
> 必须由框架自带 `boundary`，写死了会导致文件上传彻底失效。

### 7️⃣ 页面内容顶到屏幕最上方

**现象**：标题、消息图标被状态栏的时间和刘海压住。

**根因**：全项目 66 个页面统一写 `padding-top: max(12px, env(safe-area-inset-top))`。
但 **`env(safe-area-inset-top)` 在小程序 / App 的 WebView 里恒为 0**
（那是浏览器 `viewport-fit=cover` 才有的东西），
所以实际 padding 只有 **12px**，而 iPhone 状态栏约 **44px**。

**佐证**：全项目此前**无一处**使用 `statusBarHeight`。

**处理**：新增 `src/utils/navbar.ts` + `main.ts` 全局 mixin。

```ts
// navbar.ts
export function getStatusBarHeight(): number {
  if (cachedHeight >= 0) return cachedHeight;
  let h = 0;
  // #ifndef H5
  try {
    // 新 API 优先，旧 API 兜底（与 uni 运行时自身写法一致）
    const u = uni as unknown as { getWindowInfo?: () => { statusBarHeight?: number } };
    const info =
      typeof u.getWindowInfo === 'function' ? u.getWindowInfo() : uni.getSystemInfoSync();
    h = (info && info.statusBarHeight) || 0;
  } catch (_) { h = 0; }
  // #endif
  cachedHeight = h;
  return cachedHeight;
}

export function navBarStyle(): Record<string, string> {
  const h = getStatusBarHeight();
  if (!h) return {};                       // H5：返回空对象，保留 CSS 的 env() 写法
  return { paddingTop: `${h + 12}px` };    // 小程序 / App：覆盖 CSS 的 12px
}
```

```ts
// main.ts —— 全局 mixin，所有组件直接可用 navStyle
app.mixin({
  computed: {
    navStyle(): Record<string, string> { return navBarStyle(); },
  },
});
```

模板里 71 处 `<view class="nav-bar">` 改为 `<view class="nav-bar" :style="navStyle">`。

**设计要点**：H5 端返回**空对象**，不覆盖 CSS 里的 `env()` 写法 —— 两端各走各的机制，互不干扰。

### 🔟 业务域名校验文件用网址访问不到

**现象**：把微信的业务域名校验文件放到服务器项目 `jianyioa` 文件夹下，用网址访问不到（404）。

**根因**：Apache 配了 `ProxyPass / http://127.0.0.1:3001/` —— **全量反向代理**，
项目根目录**不是** Web 根目录。站点根本没有传统意义上的 Web 根。
Node 端只托管三处：`/` → `web\dist`、`/m` → `public-mobile-h5`、`/uploads`。

**处理**：
1. 把 `h0wbM9UnWF.txt` 复制到 `D:\wwwroot\jianyioa\web\dist\`
2. **发现原文件开头多了一个换行**（33 字节 = 32 字符 + `\n`），
   用 `[System.IO.File]::WriteAllText` + `UTF8Encoding $false`（不写 BOM）重写为精确 32 字节
   —— 避免微信严格比对失败
3. 验证：`https://erp.fujinwanjia.com/h0wbM9UnWF.txt` → HTTP 200、`text/plain; charset=UTF-8`、
   32 字节、**字节级完全一致** ✅

> 💡 **通用经验**：本项目**没有传统 Web 根目录**。任何要「放到网站根目录」的第三方校验文件
> （微信、百度、Google 验证等）都必须放进 `D:\wwwroot\jianyioa\web\dist\`，
> 而不是项目根目录或 Apache 目录。
>
> ⚠️ **重建 PC 前端会覆盖 `web/dist`**，校验文件会丢 —— 但业务域名校验是**一次性**的，
> 通过后不再需要，所以无所谓。

**补充**：全项目**无 `<web-view>`**，所以业务域名（需上传校验文件那个）**非必需**。
真正必须的是 `request` / `uploadFile` / `downloadFile` 三个合法域名。

### 1️⃣4️⃣ 按角色隐藏 tab 在小程序端失效（待处理）

`utils/permission.ts` 的 `applyRoleTabBar()` 用 `uni.setTabBarItem({ index, visible })` 按角色隐藏 tab。
**`visible` 参数是 uni-app 私有扩展，微信小程序不支持**，会**静默失败**。

**影响**：小程序端所有角色都会看到全部 tab，权限隐藏失灵。

**可选方案**：
- A. 小程序端改用**自定义 tabBar**（`app.json` 配 `"custom": true` + 自绘 `custom-tab-bar/` 组件）
- B. 接受降级方案：tab 全显示，进去后按权限拦截

## 三、方法论沉淀

### 🔧 定位「请求到底有没有到达后端」

服务器访问日志在：`D:/BtSoft/wwwlogs/jianyioa-access.log`
（**不是** `D:\BtSoft\apache\logs` —— 宝塔的站点日志走独立目录）

### 🔬 对照实验法

排障时**一次只改一个变量**。本次登录问题就是靠「同接口 + 同凭据 + 只换 Content-Type」
三次对照，一步定位到真根因，避免了继续在密码/数据库方向瞎猜。

### 🔍 全量扫描代替逐个试错

WXSS 那两轮返工就是因为**第一轮只扫了一类问题**（反斜杠），没顺带扫 `*`。
后来改为「用 Python 扫全部 `<style>` 块 + 全部产物 wxss，一次覆盖所有已知差异」，才收敛。

### ⚠️ H5 正常 ≠ 小程序正常

今天 14 个坑里 8 个是**运行时差异**。移植前应先把这些差异列成检查清单：

1. 请求地址是否绝对化
2. 请求头是否齐全（尤其 `Content-Type`）
3. 选择器是否合法（中文 / `*`）
4. 安全区适配是否用了 `env()`（小程序恒 0）
5. 浏览器 API 是否都做了条件编译
6. tabBar 是否 ≤ 5 项、图标是否 PNG
7. 文件上传/下载 API 是否换成了 `uni.*`

## 二、审核合规（这几条是硬门槛，缺一个就驳回）

### 1. 隐私政策与授权链路 —— 目前完全缺失

实测扫描结果：`隐私` / `privacy` / `用户协议` / `requirePrivacyAuthorize` / `onNeedPrivacyAuthorization` 在 `src/` **0 命中**。

但项目实际采集了这些隐私数据：

| 采集内容 | 触发位置 | 是否需声明 |
|---|---|---|
| 手机号 | `pages/bind/phone.vue`（手动输入）、`pages/login/login.vue`（员工登录） | 必须 |
| 微信头像 | `pages/bind/index.vue` 的 `open-type="chooseAvatar"` | 必须 |
| 相册 / 相机 | `utils/upload.ts` 的 `uni.chooseImage`（`sourceType: ['album','camera']`） | 必须 |
| 项目照片/合同文件 | `pages/files/upload.vue` | 必须（属用户内容） |

**要做三件事，缺一不可：**

1. **小程序后台**：设置 → 服务内容声明 → 用户隐私保护指引，逐项勾选「手机号、头像、相册、摄像头、用户内容」，并填写用途说明。
2. **前端新增 `pages/agreement/privacy.vue`**（隐私政策正文页）+ `pages/agreement/terms.vue`（用户服务协议），从「我的」页和登录页可随时打开。
3. **首次启动弹窗**：基础库 2.32.3+ 微信会弹官方标准弹窗，但**上一版审核更认自研弹窗 + 明确勾选**。弹窗文案必须写"同意《用户隐私保护指引》"，且提供"暂不同意"（只能退到落地页，不能直接退出）。

> 注意：不配置隐私指引时，`chooseAvatar` / `chooseImage` 在真机上会直接失败，不是"可能失败"。

### 2. 提审时必须准备的东西

| 材料 | 说明 |
|---|---|
| 测试账号 | 员工账号 1 个（如财务/项目经理，能看到较多模块）+ **业主账号 1 个**（必须预先在后台把该手机号绑定到某个真实项目上）。业主端靠"手机号匹配预约记录"登录，审核员没有你的项目数据，100% 走不通。 |
| 审核备注 | 明确写"本小程序为装饰公司内部管理 + 业主查看工地工具，非公开注册。测试账号见上"。 |
| 类目资质 | 主类目建议「工具 → 企业管理」；若选「商业服务 → 装修/家装」，需上传营业执照，部分类目还要建筑业资质。 |
| **小程序备案** | 2023-09-01 后新注册小程序必须先完成备案才能提审；存量未备案的会被限制功能。域名 `erp.fujinwanjia.com` 的 ICP 备案主体要与小程序主体一致或有关联证明。 |

### 3. 内容安全（UGC 风险）

施工日志、巡检整改、项目文件都允许员工上传**自由文本 + 图片**，属于 UGC。按《微信小程序平台运营规范》，需接入内容安全检测：

- 文本：`security.msgSecCheck`（在 `server/` 侧统一拦，不要在端上做，端上能被绕过）
- 图片：`security.imgSecCheck`

现状：一条都没接。被抽查到含违规内容 → 警告/封禁风险。建议在 `server.js` 的 `project_logs` / `inspections` / `project_files` 写入前加钩子。

### 4. 分享能力（缺失但不是风险项）

`onShareAppMessage` / `onShareTimeline` **0 处**。不算驳回项，但落地页做了"先逛逛 · 看个样板工地"却分享不出去，传播链路断了。建议只给 `pages/showcase/index` 和 `pages/landing/index` 加，且用 `uni.showShareMenu` 默认开启，**不要**做任何"分享得奖励"（诱导分享是明确红线）。

## 三、包体与分包（最紧迫的工程债）

### 现状数据

> ⚠️ **口径说明**：`du -sh` 得到的是**磁盘块占用**（小文件按 4 KB 对齐），74 个页面 × 4 个文件会产生大量空洞，`du` 报 **1.8 MB**；微信后台按**实际字节**判定 2 MB 上限，实际只有 **974 KB**。本文所有体积数字统一用**实际字节**。

```
dist/build/mp-weixin  实际 974 KB（du 显示 1.8 MB）
├── pages/      约 700 KB  ← 74 个页面，全部在主包
├── components/  约 130 KB
├── common/      约 72 KB
├── static/      约 52 KB
├── utils/       约 36 KB
└── stores/       约 8 KB
```

主包距离 2 MB 上限还有 **1074 KB**。**结论要修正**：这不是"再加几个页面就爆"的紧急状态，但 74 个页面全塞主包意味着**每次冷启动都要下载并解析全部页面逻辑**，首次打开慢、后续任何功能扩张都会被主包体积拖住。分包的价值主要在**启动性能**，不在"避免构建失败"。

### ✅ 已执行（2026-10-22）—— 主包 974 KB → 424 KB（-56%）

5 个分包、57 个页面迁出主包，主包只留 17 页（5 个 tabBar 页 + 落地/登录/绑定 + 业主端全部页面）。

| 包 | 页面数 | 体积 | 内容 |
|---|---|---|---|
| **主包** | 17 | **424 KB** | landing、showcase、login、bind×2、home、mine、projects/list、inspection/list、purchase/list、customer/{home,projects,messages,mine,logs,project-detail,family} |
| `pkg-project` | 8 | 176 KB | 项目详情/节点/甘特/施工日志 |
| `pkg-inspect` | 10 | 110 KB | 巡检、验收、增减项、派工 |
| `pkg-purchase` | 7 | 90 KB | 采购、主材 |
| `pkg-finance` | 14 | 106 KB | 财务、合同、报表 |
| `pkg-misc` | 18 | 160 KB | 审批、消息、通知、通讯录、项目文件、设置、客户管理、我的日志/巡检 |
| **总包** | 74 | **1067 KB** | 距 20 MB 上限还有 19 MB |

> 总包反而增加了 93 KB（974 → 1067）：分包边界处被多个包共用的模块会被各自复制一份（uni-app 不做跨包共享）。这是分包的正常代价，用 93 KB 总包换 550 KB 主包，值。

```jsonc
// src/pages.json（实际配置）
"subPackages": [
  { "root": "pkg-project",  "pages": ["projects/add","projects/detail", ... ] },
  { "root": "pkg-inspect",  "pages": ["inspection/add","inspection/detail", ... ] },
  { "root": "pkg-purchase", "pages": ["purchase/add","purchase/detail", ... ] },
  { "root": "pkg-finance",  "pages": ["finance/list","finance/dashboard", ... ] },
  { "root": "pkg-misc",     "pages": ["approval/list","approval/apply", ... ] }
],
"preloadRule": {
  "pages/home/index":      { "network": "all", "packages": ["pkg-project","pkg-inspect"] },
  "pages/projects/list":   { "network": "all", "packages": ["pkg-project"] },
  "pages/inspection/list": { "network": "all", "packages": ["pkg-inspect"] },
  "pages/purchase/list":   { "network": "all", "packages": ["pkg-purchase"] }
}
```

**为什么业主端（`pages/customer/*`）全留主包**：业主用的是自绘 `customer-tabbar`（非原生 tabBar），7 个页面加起来只有 140 KB 左右。放进分包会导致底部 tab 切换时首次点击要等分包下载，体验反而变差。

**改造方式**（可复用）：建立「旧路径 → 新路径」映射表 → `shutil.move` 移动 57 个 `.vue` → 正则批量替换 32 个文件里的路径引用（用 `(?![\w/-])` 负向断言防止 `projects/log` 误伤 `projects/logs`）→ 重写 `pages.json`。全程无手工改路径。

**`lazyCodeLoading: "requiredComponents"`** 保留，与分包叠加生效。

> ⚠️ 构建注意：`uni build` **不会自动清空 `dist/build/mp-weixin`**，迁移后必须手动清一次旧产物，否则体积统计会把残留的旧页面算进主包（实测残留会让主包虚高到 1.5 MB）。开发机安全守卫会拦 `rm -rf`，改用 `mv` 到 `/tmp` 即可。

## 四、运维视角（发版之后才是成本）

### 1. 版本更新提示（0 处 `getUpdateManager`）

小程序发版后，用户手机上仍是旧代码，直到微信自己冷启动更新——**可能几周不生效**。必须在 `App.vue` 的 `onLaunch` 加：

```js
// #ifdef MP-WEIXIN
const um = uni.getUpdateManager();
um.onUpdateReady(() => {
  uni.showModal({
    title: '有新版本',
    content: '更新后体验更流畅，是否重启？',
    success: (r) => { if (r.confirm) um.applyUpdate(); },
  });
});
// #endif
```

否则每次发版，客服都要面对"我这边没这个按钮"。

### 2. 线上错误你完全看不见

现状：`wx.onError` / `onUnhandledRejection` / `onPageNotFound` 一个都没接，只有 `App.vue` 里给 **H5** 加了 `window.addEventListener('unhandledrejection')`。

小程序端的崩溃、白屏、接口 500，**只能靠业主打电话告诉你**。最小成本方案（半天）：

1. `App.vue` 接 `uni.onError` + `uni.onUnhandledRejection`，把 `message + stack + userInfo.id + APP_VERSION + 当前路由` POST 到后端 `/api/client-logs`。
2. 后端写一张 `client_logs` 表，后台加个 50 行的列表页。
3. `onPageNotFound` 做兜底跳首页（分包改造后 404 会变多，这个必须加）。

同时把 38 处 `console.log` 在生产构建里剔掉（`vite.config.ts` 加 `esbuild.drop: ['console','debugger']`）。

### 3. 域名与证书

小程序调用 `https://erp.fujinwanjia.com`（写死在 `utils/api.ts` 的 `API_ORIGIN`），需要三处登记齐全：

- request 合法域名：`https://erp.fujinwanjia.com`
- uploadFile 合法域名：同上（`utils/upload.ts` 走的是同一个域）
- downloadFile 合法域名：同上（`projectFileUrl()` 拼的下载地址）

**证书到期 = 小程序全站白屏**，且是"突然"的。建议给证书加到期前 30 天提醒（宝塔面板有到期提醒开关，打开它）。

> 另注：`manifest.json` 里 `"urlCheck": false` 只影响开发者工具，线上照样强校验域名。别因为在工具里能跑就以为线上能跑。

### 4. 发布节奏

- 用**分阶段发布**：10% → 50% → 100%，每档观察 2 小时。你的用户是同公司员工+业主，量小，一档 30% 就够。
- 版本号已经由 `vite.config.ts` 从 `package.json` 注入成 `__APP_VERSION__`，并在落地页底部显示——这个设计很好，**继续用**，并让它随错误日志一起上报，客服能直接问"您页面底下版本号是几"。

### 5. 后端不可用时的前端兜底

现在接口挂了的表现是：`pages/projects/list.vue` 的 `catch` 里 `return { data: [] }`，然后 `list` 保持空数组 → 用户看到"暂无项目"，**误以为数据被删了**。

必须区分"空"和"错"：请求失败时显示"网络异常，点击重试"按钮，而不是空状态。这个改动要落到统一请求封装里（见下）。

## 五、体验与性能

### 1. 统一请求封装（收益最高的一项）

现状：`src/` 里 **211 处** `uni.request` 裸调用，只有 `App.vue` 的全局拦截器在补 `x-user-id` 头和绝对地址。每处各写各的：

- 超时时间不统一（不传就是 60s 默认值，弱网下用户干等）
- 401 / 403 / 500 没有统一处理
- `showLoading` 只有 20 处用到（211 处请求里 90% 无任何加载态）
- 失败后 `catch` 各自为政，多数静默吞掉

建议新建 `src/utils/request.ts`：统一 15s 超时、统一 loading（可关）、统一错误 toast、401 清 token 并回登录页、失败自动重试 1 次（仅 GET）、可注入 `silent` 标志。然后按模块分批替换，不用一次全改。

### 2. 列表分页（现在完全没有）

`onReachBottom` / `onPullDownRefresh` 在 `src/` **0 命中**。

`pages/projects/list.vue` 请求 `/api/projects` 不带任何分页参数，一次拉全部。项目数上到 300+ 时，`setData` 一次推 300 条大对象，iOS 上会明显掉帧甚至白屏。施工日志页同理（更严重，日志是图片密集的）。

建议：所有列表页统一 `page` / `pageSize=20` + `onReachBottom` 触底加载 + `onPullDownRefresh` 下拉刷新，配 `pages.json` 里的 `"enablePullDownRefresh": true`。

### 3. tabBar 权限控制在小程序端是空转

`utils/permission.ts` 的 `applyRoleTabBar()` 调 `uni.setTabBarItem({ index, visible })`。**微信原生 `wx.setTabBarItem` 没有 `visible` 参数**——只有 `text` / `iconPath` / `selectedIconPath`。所以这段代码在小程序端只会 fail，然后被 `catch` 静默吃掉。

实际效果：设计师、主材员登录后，底部照样显示"巡检""采购"两个 tab，点进去被 `guardTab()` 踢回首页——用户会觉得"点了没反应/乱跳"。

真解法：改用 `custom-tab-bar` 自定义 tabBar（微信原生支持，`app.json` 加 `"custom": true`），权限在渲染层过滤，彻底不显示。已有的 `components/customer-tabbar.vue` 可以复用样式。

### 4. 图片链路（工地场景的命门）

- 上传：`chooseImage` 只用了 `sizeType: ['compressed']`，微信压缩后单张仍常 1~2 MB，**没有调 `uni.compressImage` 二次压缩**，也没有限制长边。
- 展示：`<image :src="absAsset(path)">` 直接拉 `/uploads/` 原图。一个相册页 20 张图 = 可能 40 MB 流量。

建议：
1. 前端上传前 `uni.compressImage({ quality: 70 })`，长边压到 1600 px（打印/看细节够用）。
2. 后端出缩略图（`?w=400` 参数或写入时生成 `xxx_thumb.jpg`），列表用缩略图，`previewImage` 才拉原图。
3. `<image>` 一律加 `lazy-load`（目前 0 处）和固定宽高（避免布局抖动）。

### 5. 冷启动停留营销页

`pages.json` 第一项是 `pages/landing/index`（营销落地页），它是 `PUBLIC_PAGES`，所以**已登录的员工每次冷启动都先看一屏"简逸装饰 · 让业主随时看见工地"**，再自己点进首页。

建议在 `App.vue` 的 `onLaunch` 里分流：有 token 且非首次启动 → `uni.reLaunch` 到 `pages/home/index`（客户身份去 `pages/customer/home`）。只有首次启动或未登录才停在落地页。审核不受影响（仍保留游客可浏览）。

### 6. 巨石页面

`pkg-project/projects/detail.vue` **3481 行**、108 KB，单文件塞了项目信息、节点、日志、文件、财务等多个模块。后果：任何改动都要全量回归；首次进入渲染慢；多人协作必冲突。

建议按 tab 拆成子组件（`components/project-detail/InfoPanel.vue` 等），页面只做容器。不用一次拆完，先把最大的 3 个 panel 拆出去。

## 六、暂时不要做（避免过度工程）

- **别上 TypeScript 强类型全覆盖**：现在只有 `stores/user.ts`、`utils/*.ts` 是 TS，页面都是 JS。全覆盖是 2 周工作量，收益为 0（审核和运维都不看这个）。
- **别引 UI 框架**（uView / TDesign）：现有自研组件 + 全局 CSS 变量已经成型，引框架会让包体回涨 300~500 KB，把分包省下来的空间又吃掉。
- **别做 SSR / 跨端统一**：H5 和 mp-weixin 两个分支已经有既存平台差异（navStyle、absAsset），强行统一会引入新 bug。维持现状，按 `MEMORY.md` 的"两端必须同步改"规则走即可。

## 十、业主端 403 —— 两套用户体系撞在一起（**2026-10-22 已修**）

### 现象
业主「郭大大」登录小程序开发工具后，控制台两条 403：

```
GET /api/acceptance?project_id=15  → {"error":"无权限查看验收"}
GET /api/inspections?project_id=15 → {"error":"该项目不在可见范围内"}
```

业主首页的「施工动态」里，**巡检记录和验收记录两类永远出不来**，而且因为 `loadDynamicList` 的 `catch` 只 `console.log`，界面上没有任何提示，看起来就像"本来就没有数据"。

### 根因
业主端 `x-user-id` 存的是 **customers.id**（家庭成员是 family_members.id），但后端所有权限中间件都把它当 **employees.id**：

| 接口 | 卡在哪 |
|---|---|
| `/api/acceptance` | `visibleScope(userId,'acceptance')` 去 `employees` 查角色 → 业主不在表里 → 空权限集 → `'none'` → 403 |
| `/api/inspections` | `relatedProjectIds(userId)` 的客户支路是 `customers.phone = (SELECT phone FROM employees WHERE id=?)`，先查 employees 拿手机号 → 业主不在表里 → 关联项目空 → 403 |

实测：项目 15「柏林山水1-1-103」的客户是「郭大大」（customers.id=5，手机 13716900747），`employees` 表里既没有这个手机号，也没有 id=5。

**更麻烦的是两张表的 id 会撞号**：`employees` 有 id 1~16，`customers` 有 id 5~14，重叠 4 个（6/11/13/14）。例如 id=14 既是财务员工「梁晓云」也是客户「国二」。所以**不能靠 id 猜身份**。

### 改法（已落地）
1. `server/middleware/perm.js` 新增并导出：
   - `resolveCustomerIdentity(userId, userType)`：`x-user-type==='customer'` 优先 → 否则先查 employees（有就返回 null，仍走员工 RBAC）→ 再查 customers → 再查 family_members（返回主账户 `customer_id`）
   - `customerProjectIds(identity)`：`SELECT id FROM projects WHERE customer_id = ?`
2. `server.js` 的 `/api/inspections`、`/api/acceptance` 加客户分支：客户只读自己名下项目，越权返回 403「该项目不在您的名下」
3. 两端 `App.vue` 请求拦截器注入 `x-user-type`（值来自 `uni.getStorageSync('userType')`，登录时已写入 `customer` / `employee`）
4. 删掉 3 处硬编码伪造头 `'x-user-id': '1', 'x-user-role': 'admin'`（customer 的 `home.vue` / `projects.vue` / `project-detail.vue`，两端共 6 处）。后端 2026-10-10 起已按 `x-user-id` 重算真实角色并覆盖该头，写死**无效**，只留越权隐患。

### 验证矩阵
| 场景 | 结果 |
|---|---|
| 业主 5 + `x-user-type: customer` → 巡检 / 验收 | 200 `[]` |
| 业主 5 **不带** type（老版本小程序兜底） | 200 `[]` |
| 业主 5 越权查项目 17 | 403「该项目不在您的名下」 |
| 设计师 12（关联项目）→ 巡检 / 验收 | 200（回归通过） |
| 财务员工 14 不带 type → 验收 | 403（**既有行为**，财务角色本无 `acceptance:read`） |
| 无 `x-user-id` | 401 |
| 业主 5 拉 `/api/projects?customer_id=5`（已删伪造头） | 200，项目 15 + 25 个节点 + 进度 24% |

> 项目 15 目前巡检 0 条、验收 0 条，所以修完首页动态也还是空的 —— 但不会再报 403，有数据就能正常显示。

### 仍未处理的同类问题（问题比 403 更大）
业主端读接口的权限逻辑是**混乱的**：没做鉴权的接口业主全都能读，做了鉴权的反而把业主挡住。

| 接口 | 现状 |
|---|---|
| `/api/project-logs/:projectId` | **完全无鉴权**，任何人知道项目 id 就能读施工日志 |
| `/api/rectification-issues` | **完全无鉴权** |
| `/api/projects?customer_id=` | 直接信任参数，不校验调用者是不是这个客户 |
| `/api/inspections`、`/api/acceptance` | 已修（本次） |

再往上还有一层：整套系统没有真正的 token 校验，`x-user-id` 可被任意伪造。上面这些都是同一层面的历史问题，不是本次引入，也不适合在一次改动里全动 —— 建议单独排一个「鉴权加固」版本，统一加 token + 服务端 session，再逐个接口补越权校验。

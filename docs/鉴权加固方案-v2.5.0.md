## 一、我的判断（先说结论）

**这个系统的权限控制目前只在界面上成立，服务端不成立。**

三个层次的问题，严重程度依次递增：

1. **身份是客户端自报的**。后端 `getUserId(req)` 从 `x-user-id` 头读，读不到再读 `body.user_id`、`query.user_id`。所以任何人只要在 URL 后面加 `?user_id=1`，后端就认为他是 admin（id=1）。现在所有"按角色过滤"的逻辑，攻击者改一个数字就能绕过。
2. **三分之一接口连"自报身份"都不要求**。326 个路由里 134 个完全没有任何身份校验，其中 56 个是 POST/PUT/DELETE（写操作 + 删数据）。我实测公网匿名可读 `/api/boss-dashboard`（老板看板）、`/api/finance/summary`（财务汇总）、`/api/project-logs/15`（项目 15 的施工日志）。
3. **密码是明文**。12 个员工的 `password` 字段全部短于 32 字符（最长 10 位），0 个 bcrypt。有 6 位纯数字的，也有姓名拼音开头的（如 `tian...`）。配合"登录接口无失败次数限制"，爆破一个财务账号是分钟级的事。

**所以这不是"补几个接口鉴权"的活，是要把认证模型换掉。** 逐个接口打补丁一定漏——326 个接口，改完 200 个还剩 126 个没人记得。正确做法是**全局默认拒绝 + 白名单**，把"漏"的方向从"忘记加校验"翻成"忘记加白名单就直接 401"。

## 三、目标模型

把现在的二元组 `(x-user-id, x-user-role)` 换成四层：

```
Principal  主体   谁：employee / customer / family（家庭成员）
Session    会话   凭证：服务端签发的 token，可撤销、可过期、可审计
Permission 权限   能做什么：沿用现有权限码 acceptance:read / purchase:finance ...
Scope      范围   能看哪些：沿用 perm.js 的 visibleScope / relatedProjectIds / customerProjectIds
```

关键变化：**主体由服务端从 token 推导，客户端不再声明身份**。前端只传 token，不传 id、不传 role。

### 3.1 为什么不用 JWT

我倾向 **opaque token + 数据库会话表**，不用 JWT：

| 维度 | opaque token（推荐） | JWT |
|---|---|---|
| 撤销登录 | 删一行记录，立即生效 | 做不到，只能等过期或维护黑名单 |
| 权限变更即时生效 | 查库/缓存 60s 内生效 | payload 里的角色会过期前一直有效 |
| 借权登录 | 签发第二条会话，天然支持 | 要额外造 claim |
| 依赖 | `crypto`（Node 内置） | 需要 `jsonwebtoken` |
| 性能 | 一次主键查询 + 内存缓存 | 免查询 |

这个系统是内部 OA，并发很低，权限经常在后台被改（大王改角色权限是常态），"改完立刻生效"比"省一次查询"重要得多。**JWT 唯一优势是省查询，而这个系统不需要省。**

### 3.2 会话表（MySQL 5.5 兼容，不用 JSON 类型）

```sql
CREATE TABLE auth_sessions (
  id                 BIGINT AUTO_INCREMENT PRIMARY KEY,
  token_hash         CHAR(64)     NOT NULL COMMENT 'sha256(token) 十六进制，不存明文',
  principal_type     VARCHAR(16)  NOT NULL COMMENT 'employee / customer / family',
  principal_id       INT          NOT NULL,
  master_customer_id INT          NULL     COMMENT '家庭成员的主账户 customers.id',
  impersonated_by    INT          NULL     COMMENT '借权：发起借权的 admin employee.id',
  user_agent         VARCHAR(255) NULL,
  ip                 VARCHAR(64)  NULL,
  created_at         DATETIME     NOT NULL,
  last_seen_at       DATETIME     NULL,
  expires_at         DATETIME     NOT NULL,
  revoked_at         DATETIME     NULL,
  UNIQUE KEY uk_token (token_hash),
  KEY idx_principal (principal_type, principal_id),
  KEY idx_expires (expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8;
```

存的是 `sha256(token)`，**不存 token 明文**。这样即使数据库被拖走，攻击者也拿不到可用凭证。

### 3.3 token 格式与生命周期

```
token = crypto.randomBytes(32).toString('base64url')   // 43 字符
```

| 端 | 有效期 | 续期方式 |
|---|---|---|
| PC（浏览器） | 12 小时 | 每次请求命中后，剩余不足 2 小时自动续 4 小时 |
| 小程序 | 30 天 | 同上；`uni.login` 拿新 code 可无感换新 token |
| H5 | 7 天 | 同上 |

登出 = `UPDATE auth_sessions SET revoked_at=NOW() WHERE id=?`。
改密码 / 停用员工 = 按 `principal_type + principal_id` 批量 revoke。

## 五、关键实现骨架（示意，非最终代码）

### 5.1 密码迁移

不能直接改字段值（员工不知道新密码）。做法：

1. 加列 `password_hash VARCHAR(60) NULL`、`password_algo VARCHAR(10) DEFAULT 'plain'`
2. 登录时双读：`password_algo='plain'` 走旧比较，成功后立刻用 bcrypt 写入 `password_hash` 并把 algo 改成 `bcrypt`（**登录即迁移，用户无感**）
3. 管理员重置密码、员工改密码 → 直接写 `password_hash`
4. 跑 30 天后统计 `password_algo='plain'` 的残留，人工通知重置
5. 残留清零后，把 `password` 列清空（不删列，留着回滚）

> 12 个员工，也可以选"全部强制重置一次"。但我倾向登录即迁移，因为强制重置会让正在用的员工全部登不进来，还要一个个通知。

### 5.2 认证中间件

```js
// server/middleware/requireAuth.js
const PUBLIC = [
  ['GET',  /^\/api\/health$/],
  ['POST', /^\/api\/employees\/login$/],
  ['POST', /^\/api\/customers\/login$/],
  ['POST', /^\/api\/wechat\/mini-login$/],
  ['POST', /^\/api\/wechat\/mini-bind(-by-ticket)?$/],
  ['GET',  /^\/api\/wechat\/callback$/],     // 必须验微信签名，不能靠 token
  ['POST', /^\/api\/wechat\/push/],          // 同上
  ['GET',  /^\/api\/version$/],
];

module.exports = async function requireAuth(req, res, next) {
  if (isPublic(req)) return next();

  const raw = (req.headers.authorization || '').replace(/^Bearer\s+/i, '').trim();
  if (raw) {
    const s = await lookupSession(sha256(raw));       // 带 60s 内存缓存
    if (s && !s.revoked_at && s.expires_at > now()) {
      req.principal = toPrincipal(s);                 // { type, id, masterCustomerId, impersonatedBy }
      req.headers['x-user-id'] = String(s.principal_id);  // 过渡期兼容旧代码
      touch(s);                                        // 异步更新 last_seen / 续期
      return next();
    }
    return res.status(401).json({ error: '登录已失效', code: 'TOKEN_INVALID' });
  }

  // 双轨期：没有 token 才回落旧逻辑
  if (process.env.AUTH_MODE !== 'strict') {
    const uid = parseInt(req.headers['x-user-id']);
    if (uid) { logCompatCall(req, uid); return next(); }
  }
  return res.status(401).json({ error: '未登录', code: 'NO_TOKEN' });
};
```

两个要点：
- **`PUBLIC` 用「方法 + 正则」而不是纯路径**，否则 `GET /api/health` 放行会连带 `DELETE /api/health` 也放行。
- 过渡期仍然写 `req.headers['x-user-id']`，让 326 个接口里的旧代码不用一次改完。这是"能分批"的关键。

### 5.3 双轨开关与切换节奏

```bash
# server/.env
AUTH_MODE=compat   # compat = 认 token，无 token 回落 x-user-id 并打日志
                   # strict = 无 token 一律 401
```

| 阶段 | 动作 | 观察指标 |
|---|---|---|
| 1 | 后端上 `compat`，签发 token，前端先不发 | 无变化，验证签发不影响旧流程 |
| 2 | PC 端发版（覆盖 `web/dist` 即可） | `compat` 日志里 PC 的回落调用应归零 |
| 3 | H5 + 小程序发版 | 回落调用只剩零星 |
| 4 | 切 `strict`，观察 24h | 401 数量、客服反馈 |
| 5 | 删 `compat` 分支代码 | — |

**切换时机建议工作日晚 8 点后**，因为第 4 步一旦有人还在用旧版小程序，会直接被踢。小程序审核周期不可控，这也是我建议现在就把 P0 做完、P1 尽早进审核的原因。

### 5.4 借权登录

现在是前端把 `localStorage.user.id` 改成被借权者的 id，后端无从判断这是借权还是冒充。改造后：

```
POST /api/admin/impersonate  { employeeId }        // 需 admin 权限
→ 返回新 token，session 里 impersonated_by = 当前 admin id
→ 前端用新 token 替换，原 token 保留（退出借权时换回）
```

好处：借权行为**有痕迹**（`impersonated_by` 落在会话表里），审计日志能查到"谁借了谁的权"。

## 十、明确不做（避免过度工程）

- **不引 JWT / Passport / OAuth2**：一套内部 OA，opaque token + 一张表足够，多引一层只会增加排查成本。
- **不做 API 网关 / 微服务拆分**：326 个路由在一个文件里确实难维护，但拆服务是另一个量级的事，跟安全无关。`server/routes/` 那次重构已经失败过一次（代码至今没被引用），不要再试第二次。
- **不做前端路由级权限重构**：前端权限只管"菜单显不显示"，真正的门禁在服务端。现在前端权限位是好的，不用动。
- **不追求 100% 接口都有精细权限码**：P2 只处理数据越权（能不能看别人项目），不需要给每个接口都设计新权限位——现有 27 个模块 key 够用。

### 11.1 最容易被忽略的前提：既有权限逻辑不用重写

先把话说清楚，避免误判改造量：

| 资产 | 改造后是否保留 | 说明 |
|---|---|---|
| 27 个模块 key（`acceptance` / `purchase` / `finance` ...） | **完全保留** | 权限位设计是对的，一个字不用改 |
| 7 个角色 preset（admin / manager / designer / Engineer / finance / material / user） | **完全保留** | 同上 |

### 11.2 原方案中的错误（已修正）

**错误**：P0 写"`getUserId` 去掉 body / query 兜底"。

**为什么错**：文件预览/下载场景**无法携带自定义请求头**——`<img src>`、`<iframe src>`、`uni.previewImage` 都是浏览器/微信自己发的请求，JS 加不了头。所以代码里刻意留了 query 通道，`server.js:7355` 有明确注释：

```js
// 用于移动端审核页/详情页的预览（H5 的 <img>/<iframe> 无法携带自定义请求头，
// 故鉴权用户 ID 通过 query.user_id 传入，见 getUserId）
```

实测受影响的前端共 13 处：

| 端 | 文件 | 用途 |
|---|---|---|
| PC | `web/src/views/ProjectFiles.vue:310-311` | 项目文件内嵌预览 / 下载链接 |
| PC | `web/src/components/ProjectFilesPanel.vue:178-179` | 同上（面板版） |
| 小程序 | `src/pkg-misc/files/detail.vue:151,158` | 文件详情预览 / 下载 |
| 小程序 | `src/pkg-misc/files/review.vue:170,172` | 文件审核页预览 / 下载 |
| 小程序 | `src/pkg-misc/files/list.vue:229` | 文件列表缩略图 |
| 小程序 | `src/utils/permission.ts:236` | `projectFileUrl()` 统一拼 query 的工具函数 |

**正确处理方式（分三步，不能一次砍）**：

1. **P0 阶段**：`getUserId` 砍掉 `body.user_id`（这个真没人需要），**保留 `query.user_id`**，但只在 `/api/project-files/:id/download` 这类文件接口上生效，其他接口传了也忽略。做法是加一个 `allowQueryUid: true` 的显式开关。
2. **P2 阶段**：给文件类 URL 换**短期签名**。`sign = HMAC-SHA256(secret, fileId + exp + uid)`，URL 变成 `?uid=5&exp=1730100000&sig=abc...`。这跟现在裸传 `?user_id=5` 的区别是：签名有密钥、有期限、改一个字符就失效，伪造不了。
3. **P3 阶段**：签名 URL 稳定后，彻底删掉裸 `query.user_id`。

### 11.4 既有权限设计里已经存在的脆弱点（不是改造带来的）

这几条**现在就已经在**，改造只是会把它们暴露出来，建议一并处理：

| # | 问题 | 现象 | 影响 |
|---|---|---|---|
| 1 | `admin` 的 `permissions` 是 `[]` | 权限表里管理员一个权限位都没有，全靠代码 `isAdminRoleInfo` 特判 | 任何新写的鉴权层如果忘了这个特判，管理员立刻变废人。**这是最容易炸的一条** |

### 11.5 建议的推进顺序（把风险摊到最小）

```
第 1 步  P0-a  删 debug 接口 + 删死代码          ← 零风险，立刻可以做
第 2 步  P0-b  56 个写接口挂 requireAuth          ← 零风险（这些本来该登录）
第 3 步  P0-c  密码 bcrypt + 登录限流（双维度）    ← 低风险，登录即迁移
第 4 步  P1-a   建表 + 签发 token（不校验）        ← 零风险，纯增量
第 5 步  P1-b   中间件 compat 模式 + 三端发版      ← 中风险，有双轨兜底

```

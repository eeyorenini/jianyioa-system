# 员工微信登录绑定方案（v2 · 管理员发码版）

> 拟定日期：2026-10-22
> 状态：**待确认**（未开始编码）
> 目标版本：v2.5.0
> 变更：v1 是「员工自己输用户名密码绑定」，v2 改为「管理员生成二维码，员工扫码绑定」

---

## 1. 目标

管理员在 PC 后台员工列表点「生成绑定码」，弹出一个微信小程序码；员工用微信扫一下，小程序自动识别为员工身份并完成绑定。此后打开小程序**直接进员工首页**，不用输账号密码。

管理员可随时在后台解绑。

**员工全程不需要输入任何密码。**

---

## 2. 先回答两个问题

### 2.1 是不是更安全？—— 是，本质提升

| 维度 | 员工自己输密码（v1） | 管理员发码（v2） |
|---|---|---|
| 密码是否经过网络 | ✅ 经过（虽有 HTTPS） | ❌ **完全不出现** |
| 密码是否可能被钓鱼 | 可能 | 不可能 |
| 会不会绑错人 | 可能（手机号撞号，见 §3.1） | 不可能（管理员指定员工） |
| 谁能发起绑定 | 任何拿到账号密码的人 | 只有管理员 |
| 员工离职/换人 | 需员工自己操作或改密码 | 管理员一键解绑 |
| 凭证生命周期 | 密码长期有效 | 一次性 ticket，10 分钟过期 |

**核心优势：密码彻底退出这条链路。** 现网 12 个员工全是 6–8 位明文弱密码（`admin` 的是 `524811Nini`，多数是手机号后 6 位），只要不走密码，这些弱密码就少一个泄露面。

### 2.2 是不是更简单？—— 前端简单了，后端多一点，总体更简单

**变简单的部分**：

- 小程序端不用做员工登录表单，不用处理「密码错误 / 账号停用 / 已绑定其他微信」这些分支
- 不用改 `pages/login/login.vue` 的登录逻辑
- 不用做「绑定成功后弹窗提示」
- 员工零学习成本——扫码就完事，不用记用户名密码

**变复杂的部分**：

- 后端要加 access_token 缓存（现在没有，见 §9.2）
- 要调 `getwxacodeunlimit` 接口生成小程序码
- 要新增一张 ticket 表
- 要新增一个小程序页面 `pages/bind/scan`
- PC 端要加二维码弹窗

**净评估**：代码量差不多（约 400 行 vs 350 行），但**坑少很多**——v1 里最麻烦的「手机号撞号导致绑错人」在 v2 里根本不存在。

## 3. 三个关键判断（仍然成立）

### 3.1 【红线】手机号绝对不能作为员工的认证凭证

实测线上库，撞号是真实存在的：

| 员工 | 员工手机号 | 撞上的客户 | 客户手机号 | 性质 |
|---|---|---|---|---|
| #11 周福晋 | 13466313616 | #11 周福晋 | 13466313616 | **同一个人**（既是员工又是业主） |
| #8 刘飞龙 | 18710086163（但 username=15711080906） | #14 国二 | 15711080906 | **完全不同的两个人，号撞了** |

v2 方案下这个问题自动消失：绑定由管理员指定 `employee_id`，不经过手机号。

### 3.2 双身份是真实存在的

`wechat_users` 一行同时存 `employee_id` 和 `customer_id`。周福晋就是员工+业主双身份。

- 只有 `employee_id` → 员工首页
- 只有 `customer_id` → 业主首页
- 两个都有 → 弹「选择身份」，记住上次选择
- 两个都空 → 回引导页

### 3.3 「微信绑定」和「借权」是两回事

| | 微信绑定 | 借权（impersonate） |
|---|---|---|
| 本质 | 这台微信**是谁** | 管理员**临时变成**别人 |
| 持久性 | 持久（写库） | 临时（localStorage，重启失效） |
| 权限 | 该员工角色的**真实权限** | 目标员工权限，admin 特权全失 |
| 谁能用 | 每个员工 | 仅 admin |

## 4. 技术验证结果（已实测，2026-10-22）

| 验证项 | 结果 |
|---|---|
| 拿 `access_token` | ✅ 成功（appid `wx929dbb667ed0f876`，secret 32 位有效） |
| `getwxacodeunlimit` + `check_path: true` | ❌ **全部 41030 `invalid page`**，连 `pages/home/index` 都失败 |
| `getwxacodeunlimit` + `check_path: false` | ✅ **成功**，返回 JPEG 97KB |
| 现有 `getGlobalAccessToken()` | ⚠️ **无缓存**，每次调用都现取（微信限 2000 次/天） |

**结论与影响**：

1. 小程序码接口本身可用，但 `check_path: true` 报错说明**线上正式版本还没索引到这些页面**——可能小程序还没发布过正式版，或发布的是很老的版本。
2. 生成时用 `check_path: false` 可以绕过校验，**但如果 `page` 在线上版本里不存在，员工扫码会打不开页面**。
3. 所以：**必须先把含 `pages/bind/scan` 的新版小程序发布上线，绑定码才能真正可用**。
4. 现有 access_token 无缓存，生成二维码必须加缓存，否则管理员多点几次就可能触发日限。

## 5. 数据模型

### 5.1 新增表 `employee_bind_tickets`

```sql
CREATE TABLE employee_bind_tickets (
  id            INT AUTO_INCREMENT PRIMARY KEY,
  ticket        VARCHAR(32)  NOT NULL COMMENT '一次性票据，放小程序码 scene',
  employee_id   INT          NOT NULL COMMENT '要绑定的员工',
  created_by    INT          NOT NULL COMMENT '生成该码的管理员 id',
  expires_at    DATETIME     NOT NULL COMMENT '过期时间，默认生成后 10 分钟',
  used_at       DATETIME     NULL     COMMENT '使用时间，非空即已用',
  used_openid   VARCHAR(64)  NULL     COMMENT '哪个微信用的',
  create_time   DATETIME     NOT NULL,
  UNIQUE KEY uk_ticket (ticket),
  KEY idx_employee (employee_id),
  KEY idx_expires (expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='员工微信绑定一次性票据';
```

### 5.2 `wechat_users` 补索引

```sql
-- 1. 一个微信只有一行（当前缺失，必须补）
ALTER TABLE wechat_users ADD UNIQUE KEY uk_mini_openid (mini_openid);

-- 2. 一个员工只能绑一个微信
--    MySQL 唯一索引允许多个 NULL，所以未绑员工的业主行不受影响
```

> ```sql
> SELECT mini_openid, COUNT(*) FROM wechat_users GROUP BY mini_openid HAVING COUNT(*) > 1;
> ```

`employee_id` 字段**已存在**，无需新增。

## 6. 接口设计

### 6.1 新增 `POST /api/admin/employees/:id/bind-qrcode`（管理员）

```js
// 权限：checkPermission('employee:write') 或 isAdmin
// 入参：无（:id 是员工 id）
// 出参：
{
  success: true,
  ticket: "a1b2c3d4e5f6g7h8",
  expires_at: "2026-10-22T10:23:00.000Z",   // 10 分钟后
  qrcode: "data:image/jpeg;base64,/9j/4AAQ...",  // 小程序码
  employee: { id: 11, name: "周福晋" }
}
// 失败：
{ success: false, message: "该员工已绑定微信，请先解绑" }
{ success: false, message: "小程序码生成失败：{errcode}" }
```

**实现步骤**：

```
1. 校验员工存在且 status='在职'
2. 校验该员工未被绑定：
   SELECT id FROM wechat_users WHERE employee_id = ? LIMIT 1
   → 有结果 = 已绑定，拒绝（提示先解绑）
3. 作废该员工此前未使用的 ticket（避免多个有效码）
   UPDATE employee_bind_tickets SET expires_at=NOW() WHERE employee_id=? AND used_at IS NULL
4. 生成 ticket：crypto.randomBytes(8).toString('hex')  → 16 位
5. 写入 ticket 表，expires_at = now + 10min
6. 取 access_token（走缓存）
7. 调 getwxacodeunlimit：
   POST https://api.weixin.qq.com/wxa/getwxacodeunlimit?access_token=xxx
   { scene: ticket, page: 'pages/bind/scan', width: 430, check_path: false }
   ⚠️ check_path 必须 false（见 §4）
8. 返回 base64 图片
```

**降级策略**：小程序码生成失败（41030 / token 异常）时，返回 `qrcode: null` + `ticket`，让 PC 前端用 `qrcode` 库自己画一个**普通二维码**（内容就是 ticket），员工在小程序里手动点「扫码绑定」扫它（走 `wx.scanCode`）。

### 6.2 新增 `POST /api/wechat/mini-bind-by-ticket`

```js
// 入参：{ code, ticket }
//   code   = wx.login 拿的临时凭证（⚠️ 传 code 不传 openid，服务端自己换）
//   ticket = 扫码带进来的票据
// 出参：
{ success: true, employee: { id, name, username, role_code, role_name, permissions, is_admin } }
// 失败：
{ success: false, message: "绑定码已失效，请让管理员重新生成" }
{ success: false, message: "该绑定码已被使用" }
{ success: false, message: "该账号已停用，请联系管理员" }
{ success: false, message: "该账号已绑定其他微信，请先解绑" }
```

**实现步骤**：

```
1. code → openid（getWechatSession，服务端换，不信任前端传的 openid）
2. 查 ticket：
   SELECT * FROM employee_bind_tickets WHERE ticket=? LIMIT 1
   - 不存在 / used_at 非空 / expires_at < now  → 拒绝
3. 查员工：status 必须为「在职」
4. 唯一性检查：
   SELECT id FROM wechat_users WHERE employee_id=? AND mini_openid<>? LIMIT 1
   → 有结果 = 被别的微信占了，拒绝
5. 事务内：
   - 写/更新 wechat_users（employee_id, phone, bind_time, last_identity='employee'）
   - UPDATE employee_bind_tickets SET used_at=now, used_openid=? WHERE id=?
6. 返回员工身份 + permissions（复用 getUserPermissions / isAdmin）
```

## 7. 小程序端

### 7.1 新增页面 `pages/bind/scan.vue`

**这是扫码的落地页**，小程序码里 `page: 'pages/bind/scan'`，`scene` 就是 ticket。

```js
onLoad(async (opt) => {
  // 小程序码扫码 → options.scene；普通二维码扫 → options.q
  let scene = '';
  try { scene = decodeURIComponent(opt.scene || ''); } catch (_) {}
  if (!scene && opt.q) {
    // q 是被 encodeURIComponent 的完整路径，取 scene= 参数
    const m = decodeURIComponent(opt.q).match(/scene=([^&]+)/);
    if (m) scene = m[1];
  }
  if (!scene) { 提示"绑定码无效"; return; }

  // wx.login → code
  const code = await wxCode();
  const r = await uni.request({ url: '/api/wechat/mini-bind-by-ticket',
    method: 'POST', data: { code, ticket: scene } });

  if (r.data.success) {
    // 写入身份 → 进员工首页
    setEmployeeIdentity(r.data.employee);
    uni.switchTab({ url: '/pages/home/index' });
  } else {
    // 失败展示原因 + 「重新扫码」按钮
  }
});
```

**页面状态**：`loading` → `success`（3 秒倒计时后 `switchTab` 进首页）/ `error`（显示原因 + 「重新输入绑定码」）。

**降级通道（已实现）**：小程序码生成失败时，PC 只给出 16 位 `ticket` 文本。员工从
`pages/login/login`（员工 tab）的「已绑定微信？直接进入 · 手动输入绑定码」进入本页，
没有 `scene` 参数时页面直接进入 `input` 状态，手动输入 ticket 走同一条 `doBind()` 链路。

**审核注意**：该页面属于登录流程，要加进 `PUBLIC_PAGES` 白名单，否则会被 `checkAuth` 踢走。

### 7.5 员工「微信一键登录」入口（阶段 2）

`pages/login/login.vue` 员工 tab 顶部新增绿色「微信一键登录」按钮（`#ifdef MP-WEIXIN`，
H5 无 `wx.login` 故不渲染），走 `miniSilentLogin()` → 读 `identities`：

| 命中情况 | 行为 |
|---|---|
| 只有 employee 身份 | `saveEmployeeIdentity()` → `switchTab` 员工首页 |
| employee + customer | 存 `wxLoginResult` → 进 `pages/identity/select` 让用户选 |
| 只有 customer | toast「该微信是业主账号，请切到客户登录」，不跳转 |
| 都没有 | toast「该微信未绑定员工，请联系管理员」 |

⚠️ **关键坑**：`identities[type=employee]` 的主键叫 `employee_id`，而 `saveEmployeeIdentity()`
原先只认 `emp.id`，会静默 `return` 导致"提示成功却仍是未登录态"。已在 `utils/wechat.ts`
里做 `Number(emp.id || emp.employee_id || 0)` 兼容。

⚠️ **业主入口的兜底**：`pages/bind/index.vue`（业主一键登录）原先只判断 `r.customer`，
员工误点后会被要求填头像昵称再进客户首页。现已加分支：无业主身份但有员工身份 → 直接进工作台。

⚠️ 这张按钮解决的是「已绑定后的重复登录」，**不替代绑定码**。首次绑定仍需管理员发码
（`employee_bind_tickets` 一次性 + 10 分钟），因为员工身份不能靠手机号认（见 §3.1）。

### 7.6 「我的」页员工自查绑定状态（阶段 2）

`pages/mine/index.vue` 的「系统」菜单新增一行「微信登录」，右侧状态标签：

| 标签 | 含义 | 点击 |
|---|---|---|
| 已绑本机（绿） | 本机微信就是绑定的那台 | 弹窗：下次可直接一键登录 + 绑定时间 |
| 已绑其他机（橙） | 该账号绑的是别的微信 | 弹窗：要换本机需管理员先解绑 |
| 已绑定（灰） | 查不到本机 openid（无 code） | 弹窗：只显示绑定时间 |
| 未绑定（灰） | 该员工没绑过微信 | 弹窗：联系管理员生成绑定码 |

**新增接口** `POST /api/wechat/my-bind-status`：

- 请求：`x-user-id` + `x-user-type: employee`，body 可选 `{ code }`
- 返回：`{ success, bound, is_current, bind_time, nickname, openid_mask }`
- `is_current`：`true` 本机已绑 / `false` 绑的是别的微信 / `null` 未传 code 无法判断

⚠️ **必须校验 `x-user-type === 'employee'`**：`employees.id` 与 `customers.id` 两套自增会撞号，
不校验的话业主调这个接口会命中同号员工的绑定记录（信息泄露 + 误判）。已验证：客户身份调用返回 403。

⚠️ 换 openid 失败（code 过期/网络）时**降级为 `is_current: null`**，不能因此报错，
否则「有没有绑过」这个更重要的结论也会一起丢掉。

前端 60 秒节流（`wxBindAt`），避免每次 `onShow` 都打一次 `jscode2session`。

## 9. 后端实现要点

### 9.1 access_token 缓存（必须做）

现有 `getGlobalAccessToken(config)` 无缓存，每次现取。微信限制 **2000 次/天**，管理员多点几次就废了。

```js
// 内存缓存：{ token, expiresAt }
const tokenCache = new Map();  // key = appid

async function getCachedAccessToken(cfg) {
  const c = tokenCache.get(cfg.app_id);
  if (c && c.expiresAt > Date.now() + 5 * 60 * 1000) return c.token;  // 提前 5 分钟刷新
  const r = await getGlobalAccessToken(cfg);
  if (!r.access_token) throw new Error(r.errmsg || '获取 access_token 失败');
  tokenCache.set(cfg.app_id, {
    token: r.access_token,
    expiresAt: Date.now() + (r.expires_in || 7200) * 1000,
  });
  return r.access_token;
}
```

⚠️ 多进程部署时内存缓存不共享，会各取一份。当前是单进程 `node server.js`，够用；若上 pm2 cluster 需换 Redis 或落库。

### 9.2 小程序码调用

```js
async function generateMiniCode(ticket, cfg) {
  const token = await getCachedAccessToken(cfg);
  const body = {
    scene: ticket,               // 最长 32 字符，我们的 16 位够
    page: 'pages/bind/scan',
    width: 430,
    check_path: false,           // ⚠️ 必须 false，true 会 41030
  };
  // POST，返回二进制；若 content-type 是 json 说明失败
}
```

### 9.3 ticket 清理

定时任务（每小时）删过期 7 天以上的 ticket，避免表膨胀：

```sql
DELETE FROM employee_bind_tickets WHERE expires_at < DATE_SUB(NOW(), INTERVAL 7 DAY);
```

## 10. 安全设计

| 项 | 做法 |
|---|---|
| 谁能生成绑定码 | 仅 `isAdmin` 或 `employee:write` 权限 |
| ticket 强度 | `crypto.randomBytes(8)` → 16 位十六进制，不可枚举 |
| 有效期 | 10 分钟 |
| 一次性 | `used_at` 非空即失效，事务内标记防并发 |
| 重复生成 | 生成新码时作废该员工此前所有未使用 ticket |
| 员工唯一绑定 | `uk_employee` 唯一索引 + 应用层检查 |
| 微信唯一 | `uk_mini_openid` 唯一索引 |
| 离职失效 | `mini-login` 每次校验 `status='在职'` |
| 审计 | ticket 表记录 `created_by` / `used_openid` / 时间，可追溯 |
| 密码 | **全程不出现**，弱密码问题与绑定链路解耦 |

**唯一残留风险：二维码截图转发。** 谁扫谁就绑成该员工。缓解手段：

- 10 分钟过期 + 一次性
- 管理员当面让员工扫（推荐流程）
- 绑定后表格立刻显示「已绑定」，管理员能发现异常

如果要求更严，可以加「仅限公司 WiFi 网段」或「生成时弹窗显示员工姓名让管理员核对」——但当前 12 人规模没必要。

## 12. 风险与对策

| 风险 | 场景 | 对策 |
|---|---|---|
| **小程序未发布导致码打不开** | 线上版本没有 `pages/bind/scan` | **必须先发版**；生成时 `check_path:false` 只能绕过校验，页面不存在照样打不开 |
| access_token 超限 | 管理员频繁生成码 | 内存缓存 + 提前 5 分钟刷新 |
| 二维码被转发 | 截图发到群里 | 10 分钟 + 一次性 + 绑定后表格即时显示 |
| 员工换微信 | 换号/换手机 | 管理员后台「解绑」→ 重新生成码 |
| 员工离职仍能进 | 忘记停用 | `mini-login` 校验 `status='在职'`，非在职自动剔除身份 |
| 双身份用户困惑 | 周福晋既是员工又是业主 | 弹身份选择页 + 记住上次选择 |
| 业主链路被改坏 | 改造 `mini-login` 漏返 `customer` | **必须保留** `customer` / `isFamilyMember` / `masterCustomerId` 三个旧字段 |

## 13. 需要拍板的点

1. **绑定码有效期**：建议 10 分钟。要更长/更短？

   - 推荐前者，入口自然

# 业主端登录凭证方案（v2.5.1 子方案）

> 编制时间：2026-10-28
> 上位方案：`docs/鉴权加固方案-v2.5.0.md`（认证模型 = opaque token + `auth_sessions` 会话表）
> 本文只解决一件事：**业主（客户 / 家庭成员）的登录账号与密码怎么设**，以及多端如何共用一套凭证。
> 本文只做方案，未改动任何代码。

---

## 一、先说结论

| 决策项 | 结论 |
|---|---|
| 账号是什么 | **手机号**，不引入第二套账号名 |
| 密码长度 | **8–20 位** |
| 密码组成 | **必须同时含字母和数字**；不强制大小写混合、不强制特殊字符 |
| 禁止项 | 纯数字、连续/重复串、手机号任意连续 8 位、姓名拼音、生日 |
| 初始密码怎么给 | **一次性激活码**（不用短信），项目经理在 PC 生成后当面/微信发给业主 |
| 密码存储 | **scrypt 哈希**（Node 内置 `crypto`，不加依赖），绝不存明文 |
| 微信一键登录 | **保留**，但绑定必须由后端用微信 `getPhoneNumber` 解密手机号，不再信前端传值 |
| 多端 | 同一张凭证表，手机号+密码 / 微信 openid / 未来企微 userid 都是「同一主体的不同凭证」 |
| 会话 | 登录成功签发 opaque token，存 `auth_sessions`（沿用 v2.5.0） |

## 二、现状体检（2026-10-28 实测）

### 2.1 三个已经成立的安全问题

| # | 问题 | 实测证据 | 严重度 |
|---|---|---|---|
| 1 | **只凭手机号就能登录业主端** | `POST /api/customers/login {"phone":"13716900747"}` → 200，直接返回完整客户档案（id / 姓名 / 地址 / 客户编号） | 🔴 |
| 2 | **微信绑定接口不做任何校验** | `POST /api/wechat/bind {"phone":"13716900747","openid":"attacker_fake_openid_test"}` → 200「绑定成功」，任意手机号可绑到任意 openid | 🔴 |
| 3 | **身份靠请求头自报，可任意伪造** | `GET /api/projects?customer_id=5` 带 `x-user-id: 5` + `x-user-type: customer` → 200，返回项目 15「柏林山水1-1-103」完整数据 | 🔴 |

> 第 1、2 条是本文要解决的。第 3 条是 v2.5.0 的 P1（token 改造）负责的范围。
> **必须清楚：只做本文的密码，不做 P1 的 token，第 3 条依然能绕过一切登录。** 密码是门锁，token 是墙体。

### 2.2 数据结构现状

- `customers` 表 **28 列，没有 `password`、没有 `account`** —— 业主端从来没有密码这回事。
- `family_members` 表：家庭成员可独立登录，`is_master=1` 或 `relation='本人'` 的行与主账户是**同一个人、同一手机号**。
- `wechat_users` 表：已有 `mini_openid` / `mp_openid` / `unionid` / `phone` / `customer_id` / `employee_id`，可复用。
- 客户只有 **5 条**，家庭成员 7 条 —— 迁移成本极低，可以放心定规则。
- **无短信通道**（全项目无短信 SDK、无短信配置），所以"短信验证码"不是现成选项。

### 2.3 已存在的数据陷阱

- `employees.id` 与 `customers.id` **撞号**：客户 id=11「周福晋」与员工 id=11「周福晋」是同一人但两条记录；客户 id=14「国二」的手机号 15711080906 与员工 id=8「刘飞龙」相同。
  → 业主端登录**必须显式带 `x-user-type: customer`**，绝不能靠 id 猜身份。
- 家庭成员的手机号可能与主账户相同（主账户本人），也可能不同（配偶/子女）。
  → 凭证表必须**按手机号唯一**，一行指向正确的身份，不能按人唯一。

## 三、账号体系设计

### 3.1 为什么账号就用手机号

1. 手机号已经是客户的**唯一认证标识**（现有业务规则，改动成本极高）。
2. 装修业主多为非专业用户，多记一个"账号名"只会增加"我账号是啥"的客服量。
3. 未来 APP / 企微 都是同一个自然人，手机号是最稳定的跨端锚点。

**代价**：手机号本身是半公开信息（工地公示、物业登记、材料商），所以**手机号绝不能单独作为凭证**，必须配密码或微信绑定。

### 3.2 凭证表（新建 `customer_auth`）

不复用 `customers` 加列，理由：
- 家庭成员也要登录，但 `family_members` 是另一张表；
- 未来 APP / 企微 会挂更多凭证字段，塞进业务表会越塞越乱；
- 密码相关的失败计数、锁定时间、强制改密标记，不该污染客户档案。

```sql
-- MySQL 5.5 兼容：不用 JSON 类型、不用 DATETIME DEFAULT CURRENT_TIMESTAMP
CREATE TABLE customer_auth (
  id                 INT AUTO_INCREMENT PRIMARY KEY,
  phone              VARCHAR(20)  NOT NULL COMMENT '登录账号，11 位手机号',
  customer_id        INT          NOT NULL COMMENT '主账户 customers.id（家庭成员也指向主账户）',
  family_member_id   INT          NULL     COMMENT '非空=以家庭成员身份登录',
  password_hash      VARCHAR(255) NULL     COMMENT 'scrypt$N$salt$hash，空=未激活',
  password_algo      VARCHAR(16)  NOT NULL DEFAULT 'scrypt',
  must_change        TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '1=首登强制改密',
  fail_count         INT          NOT NULL DEFAULT 0,
  locked_until       DATETIME     NULL,
  last_login_at      DATETIME     NULL,
  last_login_ip      VARCHAR(64)  NULL,
  password_updated_at DATETIME    NULL,
  status             TINYINT(1)   NOT NULL DEFAULT 1 COMMENT '0=停用（客户结项/拉黑）',
  created_at         DATETIME     NOT NULL,
  updated_at         DATETIME     NOT NULL,
  UNIQUE KEY uk_phone (phone),
  KEY idx_customer (customer_id),
  KEY idx_family (family_member_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8;
```

**一行 = 一个手机号 = 一个可登录的人**。主账户本人只有一行（`family_member_id` 为空，指向 `customer_id`）；配偶/子女各一行（`family_member_id` 非空，`customer_id` 仍指向主账户，用于查项目）。

### 3.3 激活码表（新建 `customer_activate_codes`）

```sql
CREATE TABLE customer_activate_codes (
  id          INT AUTO_INCREMENT PRIMARY KEY,
  phone       VARCHAR(20) NOT NULL,
  code_hash   CHAR(64)    NOT NULL COMMENT 'sha256(code)，不存明文',
  expires_at  DATETIME    NOT NULL,
  used_at     DATETIME    NULL,
  created_by  INT         NOT NULL COMMENT '生成人 employees.id',
  created_at  DATETIME    NOT NULL,
  KEY idx_phone (phone),
  KEY idx_expires (expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8;
```

6 位数字，**7 天有效、只能用一次**，生成与使用都写 `system_logs`（谁发的、谁用的、什么时候）。

## 四、密码规则

### 4.1 规则表

| 项 | 规则 | 理由 |
|---|---|---|
| 长度 | 8–20 位 | 员工 6 位偏弱；20 位以上老人容易输错 |
| 组成 | **至少 1 个字母 + 1 个数字** | 挡住纯数字弱口令，又不至于让老人记不住 |
| 大小写 | **不强制混合** | 业主端易用优先；强制混合会让大量人写在便利贴上 |
| 特殊字符 | **不强制**（允许） | 同上 |
| 禁止 | 纯数字；连续升/降序（`12345678`、`87654321`）；单字符重复（`88888888`）；手机号任意连续 8 位；姓名全拼（不区分大小写）；`19xx`/`20xx` 年份 + 月日格式的生日 | 挡掉撞库字典里最高频的一批 |
| 与旧密码 | 不能相同，也不能只改大小写 | 系统校验不区分大小写（`utf8mb4_general_ci`），只改大小写等于没改 |
| 存储 | `scrypt$N$salt$hash` | Node 内置 `crypto.scryptSync`，实测 44ms，无需装 bcrypt（避免服务器编译原生模块） |
| 传输 | HTTPS | 已有 |

**员工端建议同步升到同一规则**（10 位以上），但那是另一件事，不阻塞本文。

### 4.2 存储格式

```
password_hash = `scrypt$16384$<salt_hex>$<hash_hex>`
```

- `N=16384`（cost），写进字符串里，将来调高 cost 不影响老密码校验。
- 校验：按前缀选算法 → 用同样 salt 重算 → `crypto.timingSafeEqual` 比对（防时序攻击）。
- 迁移：`password_algo='scrypt'` 走新逻辑；历史明文（如果有）走兼容分支并**登录成功后立刻升级**（同 v2.5.0 §5.1 的"登录即迁移"思路）。

### 4.3 代码骨架

```js
// server/lib/password.js
const crypto = require('crypto');

function hashPassword(plain) {
  const N = 16384;
  const salt = crypto.randomBytes(16).toString('hex');
  const hash = crypto.scryptSync(String(plain), salt, 64, { N }).toString('hex');
  return `scrypt$${N}$${salt}$${hash}`;
}

function verifyPassword(plain, stored) {
  if (!stored) return false;
  const [algo, nStr, salt, hash] = String(stored).split('$');
  if (algo !== 'scrypt' || !salt || !hash) return false;
  const calc = crypto.scryptSync(String(plain), salt, 64, { N: Number(nStr) }).toString('hex');
  const a = Buffer.from(calc, 'hex');
  const b = Buffer.from(hash, 'hex');
  return a.length === b.length && crypto.timingSafeEqual(a, b);
}

// 业主端弱口令检查（返回 null = 通过，否则返回错误文案）
function checkCustomerPassword(pwd, phone, name) {
  const p = String(pwd || '');
  if (p.length < 8 || p.length > 20) return '密码长度需 8–20 位';
  if (!/[A-Za-z]/.test(p) || !/[0-9]/.test(p)) return '密码需同时包含字母和数字';
  if (/^\d+$/.test(p)) return '密码不能是纯数字';
  if (/^(\d)\1+$/.test(p)) return '密码不能是重复字符';
  const seq = '0123456789abcdefghijklmnopqrstuvwxyz';
  const low = p.toLowerCase();
  const asc = seq.includes(low) || seq.split('').reverse().join('').includes(low);
  if (asc) return '密码不能是连续字符';
  if (phone && String(phone).length >= 8) {
    const ph = String(phone);
    for (let i = 0; i + 8 <= ph.length; i++) {
      if (p.includes(ph.slice(i, i + 8))) return '密码不能包含手机号';
    }
  }
  if (name && /^[a-zA-Z]{8,}$/.test(p) && low.includes(String(name).toLowerCase())) {
    return '密码不能是姓名拼音';
  }
  return null;
}
```

## 五、初始密码怎么给（没有短信通道的现实解法）

三个方案对比，**推荐 A**：

| 方案 | 流程 | 优点 | 缺点 | 建议 |
|---|---|---|---|---|
| **A 激活码** | PC 生成 6 位码（7 天一次性）→ 项目经理发给业主 → 业主输「手机号+激活码」→ 自己设密码 | 不用短信；可追溯；业主自己设的记得住；码有期限 | 需要项目经理动一下手 | ✅ **推荐** |
| B 系统生成初始密码 | 系统生成 8 位随机密码，PC 可见可复制 → 业主首登强制改密 | 实现最简单 | 转达一串乱码容易抄错；首登体验差 | 备选 |
| C 短信验证码 | 手机号 → 短信码 → 登录/设密 | 体验最好、最安全 | 需要买短信服务（约 0.04 元/条）；要接阿里云/腾讯云 SDK | 客户量大后再上 |

**A 方案的完整流程：**

```
PC 客户详情页
  [生成业主登录]  → 校验该手机号在 customer_auth 里有记录
                  → 生成 6 位码，sha256 入库，7 天过期
                  → 弹窗展示："给郭大大（137****0747）的激活码 482913，7 天内有效"

业主（H5/APP）
  首次进入 → 选「手机号 + 激活码」
  → 校验码（存在、未用、未过期）
  → 进入「设置密码」页（按 §4.1 规则实时校验）
  → 设置成功 → 标记 used_at + must_change=0 → 直接签发 token 进首页

之后
  手机号 + 密码 登录
```

**为什么不预置"手机号后 6 位"当初始密码**：那等于没有密码——知道手机号的人都能算出密码，比现在只强一点点。

## 六、多端凭证统一

### 6.1 一套主体，多种凭证

```
                     ┌──────────────────────┐
                     │  Principal（主体）    │
                     │  customer_auth.id     │
                     │  → customer_id        │
                     │  → family_member_id?  │
                     └──────────┬───────────┘
                                │
        ┌───────────────┬───────┴────────┬────────────────┐
        │               │                │                │
   手机号+密码      微信 openid       企微 userid      （未来）APP 设备
   customer_auth   wechat_users      customer_auth     customer_auth
   .password_hash  .mini_openid      .qywx_userid      .device_token
```

**关键**：任一凭证验证通过，都签发**同一个 `auth_sessions` 记录**（`principal_type='customer'`）。不要为每个端各做一套登录态。

### 6.2 微信一键登录怎么接（修现有漏洞）

现状问题：`POST /api/wechat/bind` 直接信前端传的 `phone`，任何人可绑任意手机号。

正确流程：

```
小程序端
  <button open-type="getPhoneNumber" @getphonenumber="onPhone">
  → 拿到 e.detail.code（不是手机号！）
  → POST /api/wechat/phone-login { code }

后端
  1. 用 access_token 调
     https://api.weixin.qq.com/wxa/business/getuserphonenumber?access_token=xxx
     body: { code }
     → 得到真实 phone_info.phoneNumber（微信保证可信）
  2. 用该手机号查 customer_auth
     - 查到 → 绑定 mini_openid 到 wechat_users（phone 用微信返回的，不用前端传的）
              → 签发 token
     - 查不到 → 返回「该手机号未登记，请联系您的项目经理」
  3. 若该 openid 已绑定过**另一个**手机号 → 拒绝并提示，不允许静默改绑
```

要点：
- 手机号来源必须是微信服务端返回，**前端传的一律不采信**。
- `getuserphonenumber` 需要小程序**已认证**且用户点了 `getPhoneNumber` 按钮（不是静默调用），每次调用微信收 0.03 元（有免费额度）。
- 绑定关系写进 `wechat_users`，同时 `customer_auth` 保持手机号唯一。

### 6.3 未来 APP / 企微

- **APP**：手机号 + 密码（同一张 `customer_auth`）。首次登录可加设备指纹记录，异常设备要求重新验证。
- **企微**：企微 OAuth 拿 `userid` → 绑定到 `customer_auth.qywx_userid`（新增一列）→ 后续免密。**不能**用企微手机号直接当凭证，理由同 §3.1。

## 七、防爆破与可观测

| 项 | 规则 |
|---|---|
| 账号维度 | 同一手机号连续失败 **5 次 → 锁 15 分钟**（`fail_count` + `locked_until`） |
| IP 维度 | 同一 IP **50 次 / 5 分钟**（注意：公司出口是同一个公网 IP，按账号维度收紧，IP 维度只防大规模扫描） |
| 失败文案 | 统一「手机号或密码错误」，**不区分**"手机号未注册/密码错"（防枚举客户手机号） |
| 登录日志 | 成功/失败都写 `system_logs`，含 ip、user-agent |
| 告警 | 单手机号 1 小时内失败 > 10 次、单 IP 1 小时内失败 > 200 次 → 通知管理员 |

> 现有 `/api/customers/login` 会把「该手机号未注册」和「姓名与手机号不匹配」分开返回，这本身就是**客户手机号枚举器**，必须一起改掉。

## 八、与 v2.5.0 token 方案的衔接

本文只解决"第一道门"。完整链路：

```
① 凭证校验（本文）
   手机号+密码 / 激活码 / 微信 openid
        ↓ 通过
② 签发会话（v2.5.0 P1）
   auth_sessions 插一行，返回 opaque token（43 字符）
        ↓
③ 后续每个请求
   Authorization: Bearer <token>
   中间件验签 → req.principal = { type:'customer', id, masterCustomerId }
        ↓
④ 授权（v2.5.0 P2）
   customerProjectIds(principal) 限定只能看自己名下项目
```

**没有 ②③，只做 ① 等于给一扇没有门框的门装锁。**

## 九、实施步骤（建议顺序）

| 步 | 动作 | 影响面 | 风险 |
|---|---|---|---|
| 1 | 建 `customer_auth` / `customer_activate_codes` 表（迁移脚本，幂等 + `--dry-run`） | 纯增量 | 零 |
| 2 | 写 `server/lib/password.js`（scrypt + 弱口令检查）+ 单测 | 纯增量 | 零 |
| 3 | 加 `POST /api/customer-auth/activate`（激活码设密）、`POST /api/customer-auth/login`（手机号+密码） | 新接口 | 零 |
| 4 | 加 `POST /api/wechat/phone-login`（后端解手机号），**下线**旧 `/api/wechat/bind` 的信任路径 | 修漏洞 | 低（需小程序发版） |
| 5 | PC 客户详情页加「生成业主登录激活码」按钮 + 显示/复制/作废 | PC 端 | 低 |
| 6 | 移动端登录页改造：业主 tab 从「手机号」改为「手机号 + 密码」，新增「激活/首次设置」入口 | H5 + 小程序 | 中（要发版） |
| 7 | `/api/customers/login` 旧接口改为**直接 410**（或仅 `AUTH_MODE=compat` 下保留） | 后端 | 中 |
| 8 | 迁移 5 个客户：批量生成 `customer_auth` 行（`password_hash` 为空、`must_change=1`），逐个发激活码 | 数据 | 低 |

**第 1–4 步可以不打扰任何人完成**（新表新接口，旧接口先留着）。真正的"有感知"从第 6 步发版开始。

## 十、明确不做（避免过度工程）

- **不引第三方登录平台**（Auth0 / 微信以外的 OAuth）：内部装修业务，业主不会用 Google 账号。
- **不做短信**：现阶段没通道、客户量小（5 人），激活码足够。客户量到几百再上。
- **不做密码找回自助流程**：业主忘密码 → 项目经理在 PC 重新生成激活码，30 秒解决。比"邮箱找回/密保问题"简单可靠。
- **不给家庭成员单独设密码规则**：同一张表、同一套规则。
- **不强制业主 90 天改密**：装修周期就几个月，强制改密只会制造客服电话。

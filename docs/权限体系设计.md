## 二、需求理解（陛下原话 → 落地）

核心模型：**每个模块都能配「三档可见性 + 五类动作」，"关联可见"由项目关联角色决定。**

- **三档可见性**：不可见 / 只看我参与的项目 / 看全部
- **五类动作**：读 / 写 / 删 / 审核 / 财务
  - 「财务」动作**不止催收**：还覆盖 **增减项、合同**（金额类业务）以及**关联人数据的查看**（详见第七节）
- **关联人**：项目的 创建人 + 设计师 + 工程监理 + 工长 + 该项目的客户
- **转折关系**：能看项目 → 就能看该项目下的 日志 / 巡检 / 派工 / 验收 / 增减项 / 催收，以及**该项目的客户**

逐模块对照：

| 模块 | 配置方式 |
|---|---|
| 项目管理 | 关联可见（创建人 + 四类角色）；后台可给某角色开「全部数据」（如财务）；新建项目单独配 `project:write` |
| 施工日志 | 工长 / 设计师 / 关联客户 可读；监理可读写 |
| 质量管理(巡检)、验收、派工 | 同原则：`read` / `write` / `read_all` |
| 主材管理 | 主材员 `write`，其他人 `read` |
| 增减项 | 同原则 + `approve` |
| 催收记录 | 归属财务；单独"可操作"权限 |
| 通讯录 | 默认开放范围可配 + 内部 / 外部人员区分 |
| 甘特图 | 随「项目管理」可见 |
| 客户 | 谁创建谁看 **+ 项目关联人可看** |
| 客户端(业主) | 单独一组「业主可见内容」配置 |

## 四、模型设计

### 4.1 模块清单

保留现有 23 个，**新增 3 个**（把混在别的模块里的子功能拆出来，才能单独设置）：

| 新增 key | 名称 | 来源 |
|---|---|---|
| `project_log` | 施工日志 | 现混在 `project` |
| `material` | 主材管理 | 现混在 `purchase` |
| `collection` | 催收记录 | 现混在 `finance` |

### 4.2 关联规则（"我关联的项目"）

对某用户，`关联项目集合` = `projects` 表中满足以下任一条件的项目：

```
creator_id = 我  OR  designer_id = 我  OR  supervisor_id = 我
OR  foreman_id = 我（新增）  OR  customer_id = 我（若我是客户）
```

### 4.3 数据范围（每个模块统一）

```
可见性 = 不可见 | 关联可见 | 全部可见
动作   = read / write / delete / approve / finance
```

- **不可见**：菜单隐藏 + 接口返回 403
- **关联可见**：列表 / 详情只返回 `关联项目集合` 内的数据
- **全部可见**：返回全部数据

### 4.4 项目子数据统一口径

日志 / 巡检 / 派工 / 验收 / 增减项 / 催收，均通过 `project_id` 归属项目，
其可见性直接**继承"我是否能看到该项目"**（要么是关联项目，要么有该模块的 `read_all`）。

### 4.5 客户模块（转折关系）

- 谁创建 → 看得到
- 我也是该项目关联人（设计师/监理/工长/创建人）→ 看得到该项目的客户
- 有 `customer:read_all` → 看全部

### 4.6 客户端（业主）可见内容

> ⚠️ **前提**：以下开关是「**在已关联的前提下**」进一步收窄。即客户端能否看到某类内容，
> 必须先满足 **该记录所属项目与业主相关联**；不相关的项目，一律不可见，开关不生效（详见第七节）。

在 `Roles.vue` 新增**第 5 个页签「客户端可见」**（✅ 已批示：默认值见下表，且**必须可配置**）。
> 现实情况：`roles` 表**无 `customer` 角色**（业主在 `customers` 表），故这 8 项**全局一份**，
> 存 `system_settings`（新增 `category='customer_visibility'`），后台单独配置页。
配置项建议：

| 配置项 | 说明 |
|---|---|
| 项目信息 | 项目名称 / 进度 / 节点 |
| 施工日志 | 是否可见 |
| 巡检记录 | 是否可见 |
| 验收记录 | 是否可见 |
| 整改单 | 是否可见 |
| 合同金额 | 是否可见 |
| 家庭成员 | 是否可见（增删成员） |
| 消息通知 | 是否可见 |

## 五、默认策略（✅ 已对齐 —— 2026-10-11 陛下批示）

> 详细版见 `docs/权限体系-待批示单.md`（含完整可配矩阵、各角色预置初值、8 开关明细）。

### 5.1 "未配权限"改成什么？✅ 定案：不可见（三档）

现状 `canSee()` 是 **"未配 = 不限制"**（漏配 = 全开），危险。**改为三档**：

| 档位 | 条件 | 菜单 | 数据范围 |
|---|---|---|---|
| ① 不可见 | 该模块**一个码都没配** | 隐藏 | 403 |
| ② 仅关联可见 | 配了 `read`（无 `read_all`） | 显示 | 只看关联 |
| ③ 全部可见 | 配了 `read_all` | 显示 | 全部 |

并**给现有 7 角色预置一套默认权限**（P5 迁移写入），保证一改不锁死现有同事。

### 5.1.1 配置驱动原则（陛下重点）✅

- **权限唯一真源 = `roles.permissions`（数据库），代码不得再"按角色写死"业务判断。**
- 后台「角色权限」必须提供**完整可配矩阵**：**26 个模块 × 各动作列**全部可勾选（`read_all/read/write/delete/approve/finance/salary/reset_password`）。
- 除 `admin`（直通）外，**所有角色都能被 admin 手动配出任意权限组合**；业务规则变化时**只改配置、不改代码**。
- 5.2 的清单**仅作预置初值**，之后一切由 admin 决定。

### 5.2 各角色默认权限建议（**仅预置初值**，后台可改）

| 角色 | 建议默认 |
|---|---|
| 项目经理 manager | 项目 `read_all` + `write`、日志 `write`、巡检 `write`、派工 `write`、验收 `read`、增减项 `write`、采购 `read` + `approve`、客户 `read_all`、员工 `read` |
| 设计师 designer | 项目 `read`、日志 `write`、巡检 `read`、验收 `read`、增减项 `write`、客户 `read`、报价 `read` + `write`、预算 `read` + `write` |
| 工程监理 Engineer | 项目 `read`、巡检 `read_all` + `write`、验收 `read_all` + `write`、派工 `read_all` + `write`、日志 `write`、通知 `read` + `write`、员工 `read` |
| 财务 finance | 财务 `read_all` + `write`、催收 `read_all` + `write`、采购 `read_all` + `finance`、发票 `read_all` + `write`、合同 `read_all`、收款 `read_all` |
| 主材员 material | 主材 `read_all` + `write`、仓库 `read_all` + `write`、采购 `read_all`、项目 `read_all`、合同 `read` |
| 普通员工 user | 项目 `read`、日志 `read`、公告 `read`、审批 `read`、报表 `read`、员工 `read`（通讯录） |
| 客户 customer | 走 4.6 的「客户端可见」配置 |

### 5.3 客户（业主）是否进员工通讯录

客户在 `customers` 表，不在 `employees` 表，**默认不进通讯录**。

## 七、本轮追加确认（2026-10-11 晚，陛下二次批示）

### 7.1 「财务」动作的范围扩大

五类动作中的「**财务**」**不再只等于催收**，应覆盖：

| 覆盖对象 | 说明 |
|---|---|
| 催收记录 | 原有 |
| **增减项** | 金额增减的财务处理 |
| **合同** | 合同金额相关处理 |
| **关联人数据的查看** | 见 7.3 |

落地：PC `Roles.vue` 给 `contract` / `project_contract` / `contract_change` 行也打开「财务」列（`hasFinance`），
使 `{module}:finance` 在这些模块上同样可配。

### 7.2 验收模块（工长类）—— 本轮已先行落地

- **权限定位**：与「施工日志 / 巡检」同级，属**工长类模块**（`acceptance:read` / `write` / `delete`）。
- **原有问题**：`acceptance` 表 + 4 条后端路由虽存在，但——
  - 移动端 `pages/acceptance/*` 是**模板死页面**（字段与后端全不匹配，`add.vue` 还漏 import `reactive`）；
  - **项目详情页没有「验收」入口**；首页「验收管理」跳转不带 projectId → 列表永远为空；
  - `acceptance.created_at` 表默认值被写死为 `2024-01-01`。
- **本轮已完成**：后端接口补齐（登录校验 + 创建人 join + `project_id/status/mine` 过滤 + `GET /:id` + 附件归一化 + 修正 created_at）；移动端 list / add / detail 三页重写；项目详情页新增「验收」页签；首页「验收管理」入口改为先选项目。
- **待后续补全**：验收的**内容与流程**（验收标准项、与整改的联动、通知、汇总统计）。

### 7.3 待办事项的「关联」原则（确认）

待办 = **"跟我有关的"**，判定顺序：

1. 记录（巡检整改 / 验收 / 派工 / 日志 …）的**提交人**本人 → 可见；
2. 记录所属**项目的关联人**（创建人 / 设计师 / 监理 / 工长 / 该项目的客户）→ 可见；
3. **与该项目无关的人** → 不可见；
4. 后台若给某人开启**「跨关联（看全部）」**（即该模块的 `read_all`）→ 不受关联限制，全部可见。

> 例：工长或监理提交的整改 / 巡检，只有**关联到该项目的设计师**能看；未关联的设计师看不到。
> 监理提交的记录，**该项目关联人**与**提交人本人**能看，其余看不到。

### 7.4 客户（业主）可见（确认）

- 客户能否看「巡检记录 / 验收 / 施工日志 …」→ 后台配置；
- **但前提是先判断关联**：只有与业主**相关联的项目**下的记录，才谈得上"看不看"；
  不相关的项目，直接不可见，配置不生效。

### 7.5 对第 6 节实施计划的补充

- **P2 后端**：待办中心 `todo/center` 的过滤口径统一为「提交人 OR 项目关联人 OR `read_all`」，与 7.3 对齐。
- **P3 后台 PC**：`Roles.vue` 三处改动 —— ① `contract` / `project_contract` / `contract_change` 打开「财务」列；② `acceptance` 归入「工长类」并保留可配；③ 新增「客户端可见」页签（见 4.6）。
- **P4 移动端**：验收模块（已提前完成）、待办列表按 7.3 过滤、客户端按 7.4 过滤。

## 八、消息提醒（✅ 已对齐 —— 2026-10-11 晚，陛下三次批示 + 四次批示定案）

> 陛下原话：**「关于消息提醒也是按照这个规则提醒，和待办事项一致。但要更多的信息，比如项目创建、节点通过等等。」**
>
> 四次批示（4 项全部答复）：① 接收人口径——**「是的」**；② 事件清单——**「没有」**（照 8.6 补齐，无加减）；
> ③ 渠道——**「短信只针对客户」**；④ 节点——**「节点是验收的，工程监理验收合格后自动通过；验收怎么写后续补上，现在没定」**。

### 8.1 核心原则：接收人 = 与待办完全同源 ✅ 已确认

消息提醒的**接收人判定**，与待办中心（7.3）用**同一套口径**，不再另立规则：

1. 记录（项目 / 节点 / 巡检 / 验收 / 派工 / 增减项 / 合同 / 收款 …）的**提交人本人** → 收到；
2. 记录所属**项目的关联人**（创建人 / 设计师 / 工程监理 / 工长 / 该项目的客户）→ 收到；
3. **与该项目无关的人 → 不收到**；
4. 后台若给某人开该模块的 **`read_all`（跨关联 / 看全部）** → 不受关联限制，全部收到。

### 8.2 与「角色消息订阅」的关系（重要）✅ 已确认

现状后台「消息订阅」页签（`roles.notification_types`，22 种）**本身是"谁能收到"的唯一依据**——只要某个角色勾了某类型，**该角色下所有人都会收到**，哪怕跟这条记录毫无关系。

**改造后两者是「与」关系**：

```
实际接收人 = ( 该项目关联人 ∪ 提交人 )
           ∩  关注了该消息类型的角色下的员工
           ∪  拥有该模块 read_all 且关注该类型的员工
           ∪  管理员（admin）
```

- **`notification_types` 降级为"关注偏好"**：决定"我愿不愿意收这类消息"，不再决定"我够不够格收"。
- **关联判定为"准入"**：决定"这条消息跟不跟我有关"。两者同时满足才推送。
- 保留一个例外开关：某角色勾了某类型且**该类型无项目归属**（见 8.4）时，仍按角色广播。

### 8.3 现状代码要改的三处（`notifyProject()`）

| 位置 | 现状 | 问题 | 改法 |
|---|---|---|---|
| 第 2 步 | 角色订阅 → 查该角色**全部员工** | 与项目无关的人也收到 | 改为"该角色员工 **∩ 关联人**" |
| 第 3 步 | 只查 设计师 / 监理 / 项目经理 / 客户 | **漏了创建人 `creator_id` 与工长 `foreman_id`** | 补齐这两类关联人 |
| 第 4 步 | 管理员无条件收到 | 合理，保留 | 保留（admin 直通） |

> 注：`foreman_id` 依赖第三节决策 #1（`projects` 新增工长字段），本项排在 P1 之后。

### 8.4 「无项目归属」的消息怎么办

公告（`notice_published`）、系统通知（`system_notice`）这类**没有 `project_id`** 的消息，无法按"关联"判定，
**仍按角色订阅广播**（谁勾了谁收）。这类消息不参与 8.1 的关联过滤。

判断依据：`notifyProject(type, projectId, ...)` 的 `projectId` 是否为空。

### 8.5 客户端（业主）消息

与 7.4 一致：**先判关联**，再看后台「客户端可见」页签里的 **「消息通知」** 开关。
不相关项目的消息，业主一律收不到，开关不生效。

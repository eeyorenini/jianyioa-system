## 问题一：导出 PDF 报 500 —— 服务器缺 Chromium

**现象**
合同编辑页点「导出 PDF」失败，接口返回 500。

**根因**
导出 PDF 依赖 puppeteer 驱动浏览器渲染。服务器执行 `npm install` 时，
puppeteer 的 postinstall **没有把 Chromium 下载下来**，`puppeteer.launch()` 直接抛错：

```
Could not find Chromium (rev. 1108766)
cache path: C:\Windows\system32\config\systemprofile\.cache\puppeteer
```

**顺带发现的隐患**：原代码只在 Mac 分支硬编码了 Chrome 路径
（`/Applications/Google Chrome.app/...`），而开发机并未安装 Chrome —— 这段是**静默失效的死代码**，
本地同样报 `Could not find Chrome`。也就是说该功能在本地也一直是坏的。

**修复**（`server.js`）
新增 `resolveChromePath()`，按优先级探测可用浏览器：

1. `CHROME_PATH` 环境变量（部署时可显式指定）
2. 系统安装的 Chrome / Edge（Mac / Windows / Linux 各一组候选路径）
3. puppeteer 自带的 Chromium
4. 都找不到则交回 puppeteer 报错（错误信息更完整）

启动时会打印实际使用的浏览器路径，便于确认：

```
[PDF] 使用浏览器: C:\...\chrome.exe
[PDF][warn] 未找到 Chrome/Edge，PDF 导出将失败   ← 出现这行说明没装好
```

**部署要求（关键）**
光传代码不够，**服务器必须安装浏览器**。注意 PM2 以 SYSTEM 身份运行，
它查找的是 `systemprofile` 下的缓存目录，因此要显式指定：

```cmd
cd /d D:\wwwroot\jianyioa\server
set PUPPETEER_CACHE_DIR=C:\Windows\system32\config\systemprofile\.cache\puppeteer
npx puppeteer browsers install chrome
pm2 restart jianyioa
```

## 问题二：上传图片报 500，且日志里看不到失败原因

**现象**
工具栏「上传图片」失败，返回 500；后台系统日志里该条记录 `error_message` 字段**是空的**。

**根因**
multer 的 `fileSize` 限制为 50MB。文件超限时 multer 抛出 `MulterError`，
但项目**从未注册 multer 错误处理器**，于是落到 Express 默认错误处理器：

- 返回 **HTML 堆栈 + 500**（而不是 JSON）
- 前端 axios 只能拿到笼统的"失败"，看不到原因
- 全局日志中间件依赖 `res.errorMessage`，而没人给它赋值 → 日志里原因是空的

**修复**（`server.js`）
在**所有路由之后、`app.listen` 之前**注册 multer 错误处理器，
把 `MulterError` 统一转成 **400 + JSON**，并写入 `res.errorMessage` 供日志记录。

> ⚠️ **踩坑记录**：错误处理器必须注册在**所有路由之后**。
> Express 只在出错位置*之后*的中间件里寻找错误处理器，
> 注册在路由前面**永远不会被命中**（初次修复就是这样失效的）。

同时给 `upload-image` 的 catch 补上 `res.errorMessage`。

**验证**

| | 修复前 | 修复后 |
|---|---|---|
| 上传 60MB 文件 | 500 + HTML 堆栈 | **400** `{"error":"文件超过 50MB 上限"}` |
| 日志 `error_message` | 空 | `MulterError LIMIT_FILE_SIZE: 文件超过 50MB 上限` |

## 问题三：上传图片报 `nu is not a constructor (evaluating 'new Sr')`

**现象**
压缩后的报错信息，`nu` / `Sr` 是构建产物的混淆变量名，肉眼完全看不出问题在哪。

**根因**
`Contracts.vue` 中：

```js
import Image from '@tiptap/extension-image'   // ← 遮蔽了浏览器全局的 Image 构造函数
```

这行把模块级变量 `Image` **遮蔽（shadow）** 了浏览器的全局 `Image` 构造函数。
而同一文件里有多处 `new Image()`（预加载图片尺寸、压缩图片），
本意是创建 DOM 图片元素，实际拿到的却是 **tiptap 的扩展对象** → 不是构造函数 → 报错。

**定位方法**（可复用）
错误里的 `Sr` 是压缩后的变量名。用构建产物反查：

```bash
grep "new Sr" dist/assets/Contracts-*.js          # 定位调用点
# 顺着 import{i as Sr}from"./index-Bf-*.js" 回溯，确认该 chunk 就是 @tiptap/extension-image
```

**修复**
把 tiptap 的导入改名为 `ImageExtension`，仅用于 `ImageExtension.configure({...})`；
`new Image()` 恢复为浏览器原生构造函数。

**顺手修复**：`ContractTemplatesEditor.vue` 存在**完全相同**的隐患，
一并改名，避免下次在模板编辑页踩同一个坑。

**验证**：新产物中 `new Sr` 出现 **0 次**，`new Image` 指向原生全局对象。

## 问题四：上传图片报「仅支持图片格式：jpg/png/gif/webp」

**现象**
用户上传的确是 jpg/png，却提示格式不支持。接口返回 400。

**根因**
前端上传前会先压缩图片：

```js
canvas.toBlob((blob) => { resolve(blob || file) }, file.type, 0.8)
```

`toBlob` 产出的是**没有文件名的 Blob**。紧接着：

```js
formData.append('file', compressedFile)   // ← 没有第三个参数
```

浏览器会把这个无名文件在 multipart 里命名为 **`blob`** —— **不带扩展名**。
后端拿到后执行 `path.extname('blob')`，得到空字符串，不在白名单内 → 判定"非图片格式"。

> 这个 bug 之所以长期潜伏，是因为**用 curl 测试时通常会手动指定文件名**
> （`-F "file=@x.png;filename=photo.png"`），而真实浏览器不会。
> 复现时要用 `filename=blob` 才能还原前端真实行为。

**修复（前后端双保险）**

1. **前端**（`Contracts.vue`、`ContractTemplatesEditor.vue`）
   显式指定文件名，由原文件名 + MIME 推导：

   ```js
   formData.append('file', compressedFile, `${baseName}.${ext}`)   // 如 photo.png
   ```

2. **后端**（`upload-image`）
   扩展名为空时，回退按 `req.file.mimetype` 推断
   （`image/jpeg`→`.jpg`、`image/png`→`.png` 等）。
   这样即使前端漏改，也不会再误判。同时把「文件名 + 类型」写入日志。

**验证**：`filename=blob` 分别配 png / jpeg / webp 三种 MIME，全部返回 200。

**遗留说明**
目前后端**只校验扩展名和 MIME，未做文件内容嗅探** —— 把 txt 改名成 `.png` 仍能上传。
本次保持原有行为、未扩大改动面；如需收紧，可后续加入 magic number 检测。

## 问题五：导出 PDF 里图片空白

**现象**
图片能正常插入合同编辑器，编辑器里也看得见；
但导出的 PDF 里，图片位置**一片空白**。
而**上传的 PDF 文件导出来是正常的** —— 这个差异是破案关键。

**根因**
- 编辑器上传图片后，插入的是**相对路径** `/uploads/logs/xxx.png`
- 后端用 puppeteer 的 `page.setContent(html)` 渲染，页面是 **`about:blank`，没有 origin**
- 相对路径无处解析 → 图片全部加载失败 → PDF 里就是空白

**上传的 PDF 为什么正常**：`/api/upload-pdf` 会把它转成
**base64 data URL**（`data:image/png;base64,...`），数据自带、不依赖任何路径，所以能渲染。

**对照实验（决定性证据）**
同一张图，只改 `src`，各自导出 PDF，再用 poppler 转成 PNG 逐像素比对：

| 场景 | PDF 体积 | 非白像素占比 |
|---|---|---|
| A 相对路径 `/uploads/...` | 5,340 B | 0.09%（只有文字，**无图**）|
| B 绝对路径 `http://127.0.0.1:3002/uploads/...` | 7,170 B | 4.64%（**图片正常**）|

修复后，A 的产物变为 7,170 B，与 B 完全一致。

**修复**（`server.js`，纯新增）
渲染前补一个 `<base>` 标签，让相对路径指向本机后端：

```js
const LOCAL_BASE = `http://127.0.0.1:${PORT}/`;
function withLocalBase(html) {
  // 在 <head> 后插入 <base href="...">，已有则跳过
}

await page.setContent(withLocalBase(fullHtml), ...)   // export-pdf
await page.setContent(withLocalBase(html), ...)       // export-pdf-multi
```

**为什么用 `127.0.0.1:端口` 而不是公网域名**：
让 Chromium 直接本机取图，不依赖外网、也不依赖回环 NAT，在服务器上更稳。
（`/uploads` 与 API 同端口托管：`app.use('/uploads', express.static(uploadDir))`）

## 附：本地开发环境补充 —— poppler

`/api/upload-pdf`（PDF 转预览图）依赖系统的 `pdfinfo` / `pdftoppm`（poppler），
**不走 puppeteer**。本地 Mac 未安装该工具，因此本地该接口一直报 500
（服务器是 Windows，自带 poppler，所以线上正常）。

本地安装方式（Intel Mac 无法用 Homebrew —— 官方已放弃 Intel 支持）：

```bash
# micromamba：单文件、装在家目录，不需要 sudo
curl -sSL https://micro.mamba.pm/api/micromamba/osx-64/latest | tar -xj -C /tmp bin/micromamba
mkdir -p ~/.local/bin && mv /tmp/bin/micromamba ~/.local/bin/ && chmod +x ~/.local/bin/micromamba
export MAMBA_ROOT_PREFIX=$HOME/micromamba
~/.local/bin/micromamba create -y -p $HOME/micromamba/envs/poppler -c conda-forge poppler
```

`ecosystem.config.js` 中已加入 PATH 注入（**仅在目录存在时生效**，
服务器上不存在该目录，配置原样生效、不受影响）：

```js
const POPPLER_BIN = path.join(process.env.HOME || '', 'micromamba/envs/poppler/bin');
if (fs.existsSync(POPPLER_BIN)) BACKEND_ENV.PATH = `${POPPLER_BIN}:${process.env.PATH}`;
```

> ⚠️ 改完必须用 `pm2 start ecosystem.config.js --only jianyioa-backend --update-env` 重读配置。
> `pm2 restart <name>` 用的是已存配置，**不会**重读 ecosystem 文件。

## 部署注意

1. **必须重启 PM2**。拷贝文件不会重载已在内存中运行的旧进程 ——
   前端 `web/dist` 是静态文件、即改即生效，容易造成"前端更新了、后端没更新"的错觉。
2. 覆盖时**不要动** `server/.env` 和 `server/uploads/`。
3. 服务器装 Chromium 时注意缓存目录（见问题一）。
4. 改完前端后，浏览器需**强制刷新**（`Ctrl+Shift+R` / `Cmd+Option+R`），
   否则仍会加载缓存的旧 JS chunk。

### 判断新代码是否生效

给 `/api/upload-image` 传一个 **超过 50MB** 的文件：

| 响应 | 含义 |
|---|---|
| `500` + HTML 堆栈 | 仍是旧代码 |
| `400` + `{"error":"文件超过 50MB 上限"}` | 新代码已生效 |
